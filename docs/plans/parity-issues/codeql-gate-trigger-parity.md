# Parity issue draft — CodeQL gate trigger narrowing, sibling security workflows left un-narrowed

**Status: draft, not filed.** This file records the parity gap the trigger-narrowing work on the CodeQL alert gate (the work that added a documents-only `paths-ignore` to its `push` trigger and a code, dependency, workflow and script `paths` list to its `pull_request` trigger) deliberately leaves open. No issue has been created on any tracker and nothing below has been sent to any host. The CodeQL gate's lists are the reference for any of this and are pinned in `tests/test-codeql-trigger-listing.sh`, which `make test` runs, so an edit that re-widens that workflow's triggers or adds a permission scope fails the test. The narrowing itself is decided and recorded in the [trigger-narrowing plan](../2026-11-07-codeql-gate-trigger-narrowing.md) and is documented in the [CodeQL local scan howto](../../howto/codeql-local-scan.md) and the [repo CI watch howto](../../howto/automation-repo-ci-watch.md).

## Affected area

The pull-request and push triggers of the repository's other security workflows — `secret-scan.yaml` (gitleaks), `security-scan.yaml` (gosec) and `dependency-review.yaml` — in `.github/workflows/`, and by extension the same "gate on every change" spend pattern in `ci.yaml`, whose `paths-ignore` is coarser than the CodeQL gate got. The CodeQL workflow itself is now consistent: its `push` trigger ignores `docs/**`, `CHANGELOG.md` and `**/*.md`, and its `pull_request` trigger only fires on Go, dependency, workflow, web-app, script and other code paths, so a change that cannot introduce a finding starts no gate run. The `owasp-zap.yaml` workflow is not part of this gap: it runs only on `workflow_run` of the Release workflow and on manual dispatch, where the release is the thing under test and no path filter applies.

## Current behavior

CodeQL is the only security gate in the repository whose triggers are narrowed to the paths a finding could come from. The three sibling security workflows still run on any change they are triggered by with no `paths` or `paths-ignore` at all: gitleaks and gosec on **every** push to `main` and **every** pull request against `main`, and dependency-review on **every** pull request against `main`. So a push that only touches `docs/**`, `CHANGELOG.md` or any other `.md` file — exactly the case the operator called out as "spending runs where it cannot find anything" — still starts a full gitleaks run, a full gosec run and a dependency-review run, and each of those claims a runner for minutes. The pattern is inconsistent inside one directory of workflow files: the gate this work fixed does not fire on a documents-only push, while its two push-triggered neighbors do, and no pull request can avoid all three, which makes the run log read as though the repository still treats document changes as security-relevant everywhere except in CodeQL. `ci.yaml` sits between the two positions: its `paths-ignore` covers `docs/**`, `*.md` (root-level .md files including `CHANGELOG.md`), and the issue/PR templates, but not `**/*.md` in non-docs subdirectories, so a push that touches a `.md` file outside `docs/` still burns its full CI run.

## Expected behavior

Each security and CI workflow fires only on the paths it can actually evaluate, so that a change that cannot produce a finding for that scanner starts no scan run for it, the way the CodeQL alert gate now does. Concretely: the gitleaks, gosec and dependency-review triggers carry path filters matching the code, dependency and script surfaces of the repository (mirroring the CodeQL `pull_request` paths list where the scanner looks at the same files), and `ci.yaml`'s `paths-ignore` is widened to `**/*.md` so non-docs subdirectory .md files are also excluded, matching the CodeQL gate's full documents-only set. Scheduled and manual runs of those workflows are unaffected by path filters and keep running exactly as they do now, which is the same carve-out the CodeQL gate relies on for its Monday schedule. Nothing about what any scanner reports when it does run changes — this is trigger-surface parity, not a change to findings, thresholds or gate behaviour.

## Suggested next step

File one issue (datawatch, not datawatch-app — the affected workflow files live in this repository's `.github/workflows/`) titled along the lines of "Narrow when the secret-scan, security-scan and dependency-review workflows run, same as the CodeQL gate", and decompose it into one task per workflow plus one for the `ci.yaml` `paths-ignore` widening, each task verifying its own workflow file with `actionlint` or an equivalent trigger check (the CodeQL gate does exactly this with `tests/test-codeql-trigger-listing.sh`, wired into `make test`) and confirming on a real push that a documents-only change no longer starts that workflow while a code change still does. While drafting the per-workflow path lists, keep a shared comment or a small note naming the CodeQL gate's lists as the reference set, so the four lists stop drifting apart again. This draft file can be copied verbatim into the issue body.

## Parity surface

The gap is on the CI workflow trigger surface only. REST, MCP, CLI, comm channel, YAML/config, PWA, Android and iPhone are each intentionally excluded, with the same reason for each: no datawatch runtime code, API contract, setting or operator-visible surface changes or will change; the work is confined to the `on:` blocks under `.github/workflows/` in this repository, and the mobile clients are unaffected by how often this repository's CI spends time.
