# [sync] Verifier run cap enforced: a verifier that runs past autonomous.verifier_max_run_seconds is ended, its slot freed and retried once on the next backend

Issue: not filed (draft only; no issue has been created on any tracker)

## Affected area

The autonomous (Automata) verifier, where one verification session holds a capacity slot. This work turns the run-time cap from a stored setting into an enforced limit. The code involved is the progress-blind run clock in `internal/autonomous/verifier_run_limit.go`, the one-shot runner in `cmd/datawatch/session_judgment.go` that polls the session and ends it at the cap, the no-output error type in `internal/autonomous/one_shot_no_output.go` that carries the cap end back to callers, the end-of-cap handling in `internal/autonomous/verifier_run_cap_decision.go` (slot release, decision-log note and audit record), and the single retry on the next verifier backend in `internal/autonomous/verifier_run_cap_retry.go` and `cmd/datawatch/verifier_run_cap_retry.go`. The `cmd/datawatch/main.go` entry point is listed with this change. Each of these has a matching `_test.go` file, which covers the clock, the decision record, the retry choice and the runner's cap path.

Client surfaces affected: the PWA stats and session views, the Android and iOS apps (datawatch-app), the CLI and MCP surfaces that read PRD decision logs and the audit log, and the comm channel verbs that show a task's history. These clients see a new end reason and a new decision kind for the first time.

## Current behavior

Before this change, `autonomous.verifier_max_run_seconds` (default 2700 seconds, 0 means no cap) is read and validated, but nothing enforces it on a running verifier. A verifier that stalls without making progress is caught by the no-progress watchdog, and a session that exceeds the overall timeout is caught by the session timeout. Neither covers a verifier that keeps working but holds its slot for hours. With the change in place, the daemon now runs a progress-blind clock on each verifier. The clock adds the time between polls, and it skips intervals in which the slot state is waiting, so time spent queued for a slot does not count. When the accumulated run time reaches the cap, the one-shot runner ends the session and returns a no-output error marked as a run-cap end. That error carries the elapsed run time and the cap in seconds. The daemon writes a line to its own log with the same figures.

Clients see none of this. The run-cap end is recorded on the PRD decision log as a note of kind `verifier_run_cap`, with the note text `task=<id> elapsed_seconds=<n> cap_seconds=<n> end_reason=verifier_max_run`, and with failure category `infra`. It is also written to the audit log under the action `autonomous.verifier_run_cap`. The attempt end reason is `verifier_max_run`. No REST, MCP, CLI or comm surface yet offers a filter or a label for these values, and the apps have no locale text for them. So a capped verifier looks, to an app, like a generic failed verification with an unfamiliar note.

## Expected behavior

When the cap ends a verifier, the capacity lease it held is released once, and only if it is still held by that task, so a slot another holder took in the meantime is left alone. The decision and audit records are written even when no lease was held. The verification is retried at most once, on the next backend in the verifier order that is not the one that was capped and is not blank. If the list has no other backend, the verification is not retried. A second cap end on a retry is not retried again.

Every surface that shows PRD decisions, task history or the audit log should show a run-cap end as an infrastructure event, not as a judgment about the task. The label text is still to be chosen; a working phrase is "verifier ran past its run cap", and the final wording goes into all five locales. Each should show the elapsed time and the cap in a readable form (minutes and seconds, with the cap setting name for reference). The apps should label the decision kind `verifier_run_cap` and the attempt end reason `verifier_max_run` with that same text, and should keep unknown kinds and reasons working as they do now. Clients that show the verifier setting should say that the cap now acts, not only that it is stored.

## Suggested next step

Once the enforcement change is merged and the retry path is confirmed on a live run, open one datawatch-app issue for the Android and iOS apps and the PWA. The issue should list the exact REST and MCP fields that carry the decision kind, the note text, the attempt end reason and the audit action, the elapsed and cap values, the locale keys for the label and the help text, and the rule that a capped verification is retried at most once. Until that issue is filed, no app change is needed to keep working: the new decision kind and end reason are plain strings that existing clients will show as they show any other note, and the default cap of 2700 seconds applies on upgrade without any config change. Set the cap to 0 to turn enforcement off. This draft is a file only; no issue has been created on any tracker.
