# [sync] feat(planning-routing): planning routing config, route test and scorecard (datawatch next minor release)

Parent release: datawatch next minor release

## What changed in datawatch

Planning routing picks the planner (backend and model) for an Automaton decompose by rule, with a retry ladder. It is **off by default** and changes nothing until an operator turns it on. `shadow` records the routed decision but keeps the planner unchanged.

**This release adds four REST routes.** They are new, not changed. A mobile client needs none of them to keep working; they are the contract for a Settings card.

## New REST contract

All four are under `/api/autonomous/planning-routing`. They return 503 `autonomous disabled` when the Automata engine is off. A wrong method is 405. Errors are plain text, not JSON.

### `GET /api/autonomous/planning-routing`

Needs the autonomous read capability. Returns the config in force with its validation result. The built-in `default` ladder and the built-in risk classes are filled in under any entries the operator set.

```json
{
  "enabled": false,
  "shadow": false,
  "rules": [
    {
      "name": "security-specs",
      "match": {"kind": ["feature"], "tags": ["security"], "project": [], "risk_class": ["security"],
                "spec_size_min": 0, "spec_size_max": 0, "override": ""},
      "planners": [{"backend": "claude-code", "model": "claude-opus-5-5"}],
      "ladder": "default"
    }
  ],
  "ladders": {"default": {"touch_up_max": 1, "replan_max": 1, "escalate_after_attempts": 2}},
  "classes": {"security": {"tags": [], "path_globs": []}},
  "validation": {"valid": true}
}
```

`validation.error` is present only when `valid` is false. `rules` is always an array (empty, never null). A rule's match list fields are arrays and an empty one is a wildcard; `match` members that are unset may be absent. A ladder count of 0 reads as the default (touch-up 1, replan 1, escalate after 2).

### `PUT /api/autonomous/planning-routing`

Needs the autonomous write capability. The body is the whole block (`enabled`, `shadow`, `rules`, `ladders`, `classes`); unknown fields are refused. It **replaces** the block outright: a ladder or class left out is removed, and a missing field is its zero value (a client that wants to keep a field must send it, which is what the MCP and CLI `set` do by reading first). The result is validated before anything is applied.

- 200: the same view as GET for the block now in force. It is applied live and saved to the YAML config; one audit entry (`update`, `autonomous_planning_routing`) is written. If the YAML save fails the change still applies live and a warning is logged.
- 400: plain text. An unparseable body or unknown field starts `bad request: `; an invalid config returns the validation error text. Nothing is applied.
- 403: the caller lacks the write capability.

### `POST /api/autonomous/planning-routing/test`

Needs the autonomous read capability. Routes one input under the config in force. It calls no LLM and changes nothing.

Request (every field optional):

```json
{"kind": "feature", "tags": ["security"], "spec_bytes": 12000, "files": ["internal/auth/login.go"], "project": "datawatch", "override": ""}
```

`spec_bytes` below 0 is 400. A malformed body is 400.

Response:

```json
{
  "enabled": true,
  "rule": "security-specs",
  "classes": ["security"],
  "planners": [{"backend": "claude-code", "model": "claude-opus-5-5"}],
  "ladder": "default",
  "shadow": false,
  "fallback": false,
  "reason": "rule-matched",
  "decided_at": "2026-11-05T06:00:00Z"
}
```

`classes` and `planners` are always arrays. `fallback` is true when no rule matched (or routing is off) and the normally resolved planner is used. `reason` is one of `rule-matched`, `override`, `no-rule-matched` or `routing-disabled`.

### `GET /api/autonomous/planning-routing/scorecard`

Needs the autonomous read capability. Query `window` is a Go duration (`36h`) or a day count (`7d`); empty means 7 days and `0` means all records. A negative or malformed window is 400.

```json
{"window": "168h0m0s", "scorecard": { ... }, "gate": { ... }, "report": "plain-text gate report"}
```

`scorecard` and `gate` hold counts only, per planner and rule class: decomposes, passes by attempt, escalations, errors, and shadow would-route counts. They carry no spec or task text. `report` is the same gate report as text. The inner shapes are those of the Go `Scorecard` and `PlanningGateReport` results in `internal/autonomous`.

## Other surfaces (all proxy the REST routes above)

- MCP: `planning_routing_get`, `planning_routing_set`, `planning_routing_test`, `planning_scorecard`.
- CLI: `datawatch autonomous planning-routing` (`get`, `set`, `test`, `scorecard`).
- Comm channel: `autonomous planning-routing show | test [kind=K] [tags=a,b] [spec_bytes=N] [files=a,b] [project=P] | scorecard [window]`.
- PWA: a Settings card with a test form, the result and a counts-only scorecard; its keys are in all five locale bundles.

## Mobile handoff

- Android and iOS: **excluded from this release.** Neither is built here; this issue is the contract for adding a Settings card later.
- Nothing existing changes shape, so current clients keep working.
- Capabilities: read routes need the autonomous read capability and PUT needs the autonomous write capability; over MCP, `planning_routing_get`, `planning_routing_test` and `planning_scorecard` need the autonomous read capability and `planning_routing_set` needs the config write capability.
