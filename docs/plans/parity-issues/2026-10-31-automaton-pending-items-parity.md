## What changed in datawatch

An Automation can now carry a **pending item** as a member: a named piece of work that has no Automaton yet. datawatch keeps its own registry of pending items (a small file owned by the daemon, never read out of a document). Each item has an `id` (8 hex characters, generated by the daemon), an optional `ref` (an outside label), a `title`, a `state` (`waiting`, `attached` or `done`) and a `source` (`internal` or `file`).

- **The hold.** When the cursor of a running Automation reaches a member that is a waiting pending item, the Automation does not start anything. With the default policy `hold` it becomes `blocked`, the reason names the item, and every member after it stays behind it. With the policy `skip` the Automation passes the member over and the item stays `waiting`. The hold is not an error.
- **Attach.** Attaching an Automaton to a waiting item converts every member that carries the item, in place (same position, edges and status), into an ordinary Automaton member. The member keeps `pending_item_id` as a note of where it came from. The item moves to `attached`. With auto-resume on (the default) an Automation that was blocked on the member resumes. When the attached Automaton completes, the item moves to `done`.
- **The optional file registry.** The daemon can read a pipe table out of a file you keep and copy the rows in as pending items (source `file`). It only reads the file and never writes to it. It is read when the daemon starts and when the operator asks for a refresh. Nothing in it assumes a numbering sequence, a file name or any repository's layout: the id pattern and the columns are settings.
- **The nine settings**, all under `autonomous.automation`:
  - `pending_item_policy`: `hold` (default) or `skip`.
  - `pending_item_auto_resume`: boolean, default `true`.
  - `pending_item_source.path`: a file path; empty (default) means no file registry.
  - `pending_item_source.id_pattern`: a Go regular expression, default `^\S+$`.
  - `pending_item_source.id_column`: a header name (matched without regard to case) or a 1-based column number, default `1`.
  - `pending_item_source.title_column`: same kind of value, default `2`.
  - `pending_item_source.state_column`: same kind of value, default empty (the table has no state column).
  - `pending_item_source.done_values`: a list of words that mean the work is done, default `done`, `closed`, `shipped`.
  - `pending_item_source.on_missing_row`: `keep` (default) or `drop`, for an item whose row vanished from the file.

The PWA gained a **Pending items** card on the Overview sub-tab of the Automation screen, a **Waiting for an Automaton** badge on a pipeline member, an attach control, an insert-a-pending-item field on the insert member form, and a **Pending items** group in the Automaton settings. The Android and iPhone apps must give the operator the same information and the same actions. Capability parity is required; implementation parity is not.

## Changed REST contract

Every route needs Automata to be enabled (503 `autonomous disabled` otherwise). A federated peer needs the autonomous read capability for the `GET` and the autonomous write capability for each `POST` (403 without it); bad auth is a 401. A manager that cannot serve the registry answers 503. Error text starts with the status word: `400:`, `404:`, `409:`.

### `GET /api/autonomous/pending-items`

Read-only. Optional query parameters:

- `state` - `waiting`, `attached` or `done`. Any other word is a 400.
- `automation_id` - narrows `items` to the items an Automation carries and `held` to that Automation. An id that matches nothing is a 200 with empty lists, never a 404.

Any method other than `GET` and `POST` is a 405 with `Allow: GET, POST`.

Body:

```json
{
  "policy": "hold | skip",
  "auto_resume": true,
  "source": {
    "configured": false,
    "path": "string (empty when no file registry)",
    "id_pattern": "string",
    "id_column": "string",
    "title_column": "string",
    "state_column": "string (empty = none)",
    "done_values": ["done", "closed", "shipped"],
    "on_missing_row": "keep | drop"
  },
  "last_refresh": {
    "configured": false,
    "at": "RFC 3339 time or null (null until the file registry has been read once)",
    "rows": 0,
    "added": 0,
    "updated": 0,
    "done": 0,
    "dropped": 0,
    "kept": 0,
    "skipped": 0,
    "error": "string (empty when the last read worked)"
  },
  "items": [
    {
      "id": "string (8 hex)",
      "ref": "string (empty when none)",
      "title": "string",
      "state": "waiting | attached | done",
      "source": "internal | file",
      "automaton_id": "string (empty until an Automaton is attached)",
      "created_at": "RFC 3339 time",
      "updated_at": "RFC 3339 time",
      "attached_at": "RFC 3339 time (key absent until attached)",
      "done_at": "RFC 3339 time (key absent until done)",
      "automations": [
        {
          "automation_id": "string",
          "name": "string",
          "member_id": "string",
          "held": true
        }
      ]
    }
  ],
  "held": [
    {
      "automation_id": "string",
      "name": "string",
      "member_id": "string",
      "item_id": "string",
      "title": "string",
      "ref": "string",
      "since": "RFC 3339 time",
      "reason": "string"
    }
  ]
}
```

| Field | Meaning |
|---|---|
| `policy`, `auto_resume` | The settings in effect now (`pending_item_policy`, `pending_item_auto_resume`). An unset key reads its default (`hold`, `true`). |
| `source` | The file registry settings in effect, with every unset key shown as its default. `configured` is false while `path` is empty. |
| `last_refresh` | The last read of the file registry. Before the first read `at` is `null` and the counts are zero; show "not read yet". A failed read sets `error`. |
| `items` | Every registry item (after the `state` filter, when given). Always a list, never `null`. |
| `items[].automations` | The Automations that carry the item as a member. Always a list, never `null`. `held` is true when that Automation is blocked and the member holds its cursor. |
| `held` | One entry per Automation waiting on a waiting item right now. Always a list, never `null`. `since` is when the Automation went idle; `reason` is the note of its latest blocked decision, or a plain sentence naming the item. |

`attached_at` and `done_at` are absent keys until they have a value; `ref` and `automaton_id` are empty strings when they have none. A client must treat an absent key (and, to be safe, a `null`) as "no value".

### `POST /api/autonomous/pending-items`

Records a waiting item. Request body: `{"title": "string", "ref": "string (optional)", "actor": "string (optional)"}`. The title must not be blank and is limited in length (400 otherwise); a file item with the same `ref` is a 409. The reply is 201 with one item in the shape of `items[]` above (`automations` is an empty list).

### `POST /api/autonomous/pending-items/{id}/attach`

Attaches an Automaton to a waiting item. Request body: `{"automaton_id": "string", "actor": "string (optional)"}`. Reply 200:

```json
{
  "item": { "id": "string", "title": "string", "state": "attached", "automaton_id": "string" },
  "converted_automations": [
    { "automation_id": "string", "member_ids": ["string"], "pending_insert_ids": ["string"] }
  ],
  "resumed_automations": ["automation id"],
  "notes": ["string (key absent when empty)"]
}
```

`converted_automations` and `resumed_automations` are always lists, never `null`. `notes` says which Automations were left blocked and why (for example when auto-resume is off). Errors: 400 when `automaton_id` is missing; 404 when the item or the Automaton does not exist; 409 when the item is not waiting (so attaching twice is refused), or the Automaton is a template, a child of another Automaton, already attached to another item, or already belongs to an Automation. The app must ask for the id of an existing Automaton and show the daemon's text on a refusal.

### `POST /api/autonomous/pending-items/refresh`

Reads the file registry now. No request body. Reply 200 with the counts of the read:

```json
{
  "configured": true,
  "path": "string (key absent when not configured)",
  "at": "RFC 3339 time",
  "rows": 0,
  "added": 0,
  "updated": 0,
  "done": 0,
  "dropped": 0,
  "kept": 0,
  "skipped": 0,
  "error": "string (key absent when the read worked)"
}
```

With no registry path set, `configured` is false and nothing changes. Show the button only while `source.configured` is true.

### `pending_item_id` on insert member

`POST /api/automations/{id}/insert_member` accepts a pending item in place of an Automaton: `member.pending_item_id` (or `pending_item_id` at the top level). Give exactly one of an Automaton id or a pending item id, never both and never neither (400). `reason` and `expected_version` stay required. The item must exist (404), must be waiting, and must not be a member of another Automation (409). On a draft Automation the member lands at once; on a running Automation the insert waits for approval through the existing approve insert call, exactly like an inserted Automaton.

### The Automation JSON

- A member of the new kind **`pending_item`** carries **`pending_item_id`** and no Automaton id. The member `kind` field takes the new value `pending_item` besides the values the app already reads. An app must not crash or hide the member on a kind it does not know.
- After an attach, the same member becomes an ordinary Automaton member (the kind the app already reads for an Automaton, with its Automaton id set) and **keeps `pending_item_id`** as provenance. A member that has `pending_item_id` and an Automaton id is an attached one, not a waiting one.
- A held Automation reads `status` `blocked` (no new status value is added). Its latest decision of kind `blocked` carries the reason as a plain sentence; show it as the daemon sends it and do not parse it.
- A pending insert entry waiting for approval carries `pending_item_id` (key absent for an Automaton insert).

## What the mobile app should show

- **Card.** A **Pending items** card on the Automation screen, drawn from `GET /api/autonomous/pending-items` and refreshed no faster than every 30 seconds, beside the other Automata status cards. It has a help link, the policy line and the auto-resume line (a value this version does not know is shown as it came), the file registry line (the path, or "No file registry is configured."), the last read of the file registry (counts, the error, or "not read yet"), then the held Automations, then one row per item with its state chip (`waiting`, `attached`, `done`), its `ref`, its source (added here or file registry), the Automaton attached, the Automations that carry it, and the attach control. A failed read reads "Could not load the pending items: <message>" (or keeps the last good card marked stale), never an empty card.
- **Held list.** One row per `held` entry: "Automation <name> is waiting for an Automaton on <title>", "Waiting since <time>" and "Reason: <reason>", with the attach control.
- **Hold badge.** On the pipeline strip and member list, a member of kind `pending_item` carries the badge **Waiting for an Automaton** (tooltip: the Automation waits here until an Automaton is attached). When the member holds the cursor of a blocked Automation, make the hold easy to find. Show the item title (or "Pending item <id>" when the registry no longer knows it).
- **Attach action.** An input for the id of the Automaton to attach and an **Attach Automaton** button, on the item and on every held row. An empty id is refused on the device with "Enter the id of the Automaton to attach." After a success, re-read the card and the Automation: the member is now an Automaton member, the item reads `attached`, and the held Automation has resumed (or, with auto-resume off, show `notes`).
- **Add and insert.** An **Add a pending item** form (title, optional ref) and, on the insert member form, a choice of a waiting item (items that are not waiting, or already in an Automation, are shown as unavailable with the reason).
- **Read the file registry now.** A button shown only while `source.configured` is true; after it, show the counts.
- **Settings.** A **Pending items** group in the Automaton settings with the nine keys: policy select (hold, skip; default hold), auto-resume switch (default on), file registry path, id pattern, id column, title column, state column, done values (comma separated), and on-missing-row select (keep, drop; default keep). A key missing from the config read shows its default. The values are written through `PUT /api/autonomous/config` in its `automation` object (`pending_item_policy`, `pending_item_auto_resume` and the `pending_item_source` object with `path`, `id_pattern`, `id_column`, `title_column`, `state_column`, `done_values`, `on_missing_row`) or through `PUT /api/config` as `autonomous.automation.<key>`, and take effect without a restart. Writes are strict: a bad value (a policy that is not `hold` or `skip`, an `on_missing_row` that is not `keep` or `drop`, a pattern that is not a valid regular expression, a wrong type) rejects the whole write with a 400 that names the allowed words, and nothing changes. The app must send only allowed words and show the daemon's text on a refusal.

All of them go through the same routes and the same checks.

## Acceptance (mobile)

Both the Android and the iPhone app:

- Read `GET /api/autonomous/pending-items` with the same auth as their other Automata reads, poll it no faster than every 30 seconds, and handle 401, 403, 405 and 503 without crashing. A 503 or a failed read shows "Could not load the pending items: ..." (or keeps the last good card marked as stale), never an empty or zero card.
- Show a **Pending items** card on the Automation screen with the policy line, the auto-resume line, the file registry line, the last read of the file registry, the held Automations and one row per item.
- Treat absent keys (and `null`) as "no value": no `attached_at`, `done_at`, `ref` or `automaton_id` shows no such line; `last_refresh.at` null shows "The file registry has not been read yet."; `items`, `held` and `automations` are drawn as empty lists when absent. A key this version does not know is ignored, and a policy or state word this version does not know is shown as it came.
- Support the `state` and `automation_id` query filters (or use `automation_id` when showing the items of one Automation) and show an empty state, not an error, when they match nothing.
- Show the **Waiting for an Automaton** badge on a member of kind `pending_item`, and do not crash on, or drop, a member kind the app does not know. A member that kept `pending_item_id` after an attach is an ordinary Automaton member and carries no badge.
- Do not treat a held Automation as failed: it is `blocked` and waiting for an Automaton to be attached. Show the reason as the daemon sends it.
- Let the operator attach: send `automaton_id` to `POST /api/autonomous/pending-items/{id}/attach`, show the daemon's text on a 400, 404 or 409, and re-read the card and the Automation after a success so the member, the item and the hold update.
- Let the operator add an item (`POST /api/autonomous/pending-items`, a non-blank title, an optional ref), insert a waiting item through `insert_member` with `pending_item_id` (never together with an Automaton id), and read the file registry now (`POST /api/autonomous/pending-items/refresh`, shown only while `source.configured` is true).
- Show the **Pending items** settings group with the nine keys and their defaults. A key missing from the config read shows its default. The app never sends a word outside the allowed set, because the daemon answers that with a 400 and changes nothing.
- Add all 66 locale keys above, with the English values, to the app's own string resources in all of its languages (EN, DE, ES, FR, JA), with the English text as the placeholder in DE, ES, FR and JA until translations land. Every new string says Automaton or Automata.

Capability parity is required; implementation parity is not: each platform uses its idiomatic screens and delivery.
