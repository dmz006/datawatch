# BL461 tag browsing and tile redesign: operator decisions

Date started: 2026-10-25. The ten open questions of `docs/plans/2026-10-20-tag-browsing-tile-design.md` are answered one at a time, with the operator's words quoted. The implementation PRD reads this file and does not ask again.

## Decisions

1. **Session tags: both.** (Operator, 2026-10-25: first "1, inherit read-only", then "sessions may run outside of automation and have their own tag", then "1, both, set from the session detail and all surfaces".) A session spawned by an Automaton inherits that Automaton's tags. Any session, including one that runs outside any Automation, can also carry tags of its own. The session gets a new tags field. A session's own tags are set from the session detail page and from every surface that sets tags on Automata today: PWA, mobile apps, CLI, REST, MCP, the comm channel and the config surfaces that apply. Inherited tags are shown as inherited and are not edited on the session; they change with the Automaton.

2. **Counts: subtree counts as the main figure.** (Operator, 2026-10-25: "Q33 1 subtree counts".) Each tag shows the number of distinct items under it including its children, an item under two children counted once; the API may still return direct counts for views that want them.
3. **Attention statuses: `blocked`, `needs_review` and `paused`.** (Operator, 2026-10-25: "2".) A paused Automaton joins the attention group so every paused item is visible in one place; the `attention_statuses` setting still lets the operator change the list. **Sub-question answered (operator, 2026-10-25: "Go with your recommendations"):** an Automaton with a task held for operator review (`review_needed`) also appears in the attention group.
4. **List payload: add `tags` to each Automata list item and keep the existing task counts.** (Operator, 2026-10-25: "Go with your recommendations", for the supervisor's recommendation 1.) The tile shows progress from the counts the list already returns and tag chips from the new `tags` field, with no second request per tile; the three count fields stay as they are.
5. **Placement: both tabs, built together.** (Operator, 2026-10-25: first "1, Automata tab first", then clarified "Both all was for 37" after "Actually both,  do it now".) The tag browser is built in the Automata tab and in the Automation tab at the same time, as one shared tile component used by both, and the operator wants it built now. This replaces the earlier "Automata tab first" reading and makes the tag browser depend on the Automation tab's phase being in place.
6. **Multi-tag display: under every tag, with the "also in:" line; plus an optional primary tag for sorting.** (Operator, 2026-10-25: "1 yes both".) An item with several tags appears under every tag's branch with an "also in:" line naming its other tags, counted once per tag subtree. "Both" is read as adding option 2's primary tag as well: the operator can optionally choose a primary tag per item, used for sorting only, and it defaults to none. If "both" meant something else, the operator corrects this line.
7. **Live counts: event stream with a poll fallback.** (Operator, 2026-10-25: "1, event stream with poll fallback".) Tag counts refresh from the event stream when an Automaton's status or tags change or a tag is renamed or re-parented, and the existing poll catches up if the stream drops.
8. **Tags are federated: one shared tag registry across the federated nodes.** (Operator, 2026-10-25: "2, federation works together".) A rename or re-parent on one node reaches the others. The proposal must say how the keeper node is chosen (the same pattern as the shared usage readings), how conflicting edits are resolved, how a peer shows its last copy when the keeper is unreachable, and how a tag created on two nodes while apart is merged without hiding that they were separate.
9. **Default match mode: ANY.** (Operator, 2026-10-25: "1, ANY as default".) Selecting several tags widens the list, the filter bar shows "match ANY", and a toggle switches to ALL.

10. **Registry source for the tag tools: they are already on main.** (Answered from the code, 2026-10-25.) The MCP tools `autonomous_tag_list`, `_create`, `_rename`, `_set_parent`, `_set_color`, `_delete` are in the federation capability map and the CLI has `tag-create`, `tag-color`, `tag-delete` and `prd-set-tags`; the design document's doubt came from reading an older worktree.

**Event stream.** The `tag_update` WebSocket frame (kinds `created`, `renamed`, `reparented`, `recolored`, `deleted`, `assigned`, `session_assigned`, `registry_synced`) is a push event. It has no REST, MCP, CLI or comm form: the same data is read through the list routes. The Android and iPhone clients have no handler for it yet.

**Federation.** Tags are federated through one shared registry. The keeper is chosen by explicit configuration on each daemon (`autonomous.tags.registry_keeper`): the keeper names itself and each peer names the keeper. It is not inferred from names or addresses. A peer serves its last copy as stale while the keeper is unreachable, refuses rename, move, recolor, describe and delete with 503, and still accepts creates, which are pushed when the keeper returns. Two tags with the same name under the same parent created on two nodes while apart are merged, and a merge note records both nodes. Conflicts are resolved per field: the keeper's value wins. The keeper-to-peer routes are guarded by the autonomous capabilities.

**Sessions.** Sessions carry their own tags (decision 1). A session spawned by an Automaton shows that Automaton's tags as inherited, read-only tags. Session tags are set on every surface that sets Automaton tags, except where the table above says otherwise.
