# DataWatch Mapping — Harness Usage Patterns

**Date:** 2026-09-19 · **Status:** Draft
**Input:** `usage-patterns.md` (12 recurring patterns, 2+ builders, from the 17-builder catalog in `case-studies.md`)
**Baseline:** `AGENT.md`, `DATAWATCH-CONTEXT.md` (v8.19.8), prior research: `synthesis.md`, `enhancement-proposals.md` (2026-09-07)

Method: each recurring pattern in `usage-patterns.md` is matched against the datawatch baseline. Ratings:

- **MATCH** — datawatch implements the pattern as a first-class surface (feature + BL, or package).
- **PARTIAL** — the core exists but a named sub-capability from the practitioner evidence is absent or weaker.
- **MISSING** — no datawatch surface implements it.

Where a delta overlaps an already-proposed enhancement (Sept 2026), this file **references and differentiates** rather than re-proposing. Delta text is confined to the one-line statement per the task, with a pointer to the prior proposal where one exists.

## Gaps ranked by practitioner frequency

Ordered by how many pattern rows (and how many of the 17 builders behind those rows) touch the same delta.

### 1. No per-LLM-call request/response artifact (patterns 8, 3, 12)

- **What practitioners do:** Verma's ref registry, Storer's inspectable LLM transactions, joacod's inspector — every model call (assembled system prompt, tool schemas, input messages, output blocks, stop reason, token/cache use) is a first-class record that the harness reads back and the operator can open.
- **What datawatch lacks:** the exact-call record. `internal/audit/` (BL9) logs operator/session events, `telemetry_get` logs task/verdict state, `observer_stats` envelopes log process-level CPU/mem/net per session/backend, BL6 logs token totals — but no surface can answer "what was the 7th prompt in session X, verbatim, and what did the model say back?"
- **Differentiation:** `enhancement-proposals.md` #3 (unified lineage query + OpenInference export) closes the *query* ("what fed this output") once spans exist; the practitioner gap above is the *primitive* — persisting a span per LLM call on the inference adapters (`internal/inference/`). Proposal #3 assumes that primitive; this gap is what has to land first for both #3 and any eval sweep cost/latency table (proposal #1) to be trustworthy.

### 2. Cost and quality not wired into routing decisions (patterns 3, 7, 11)

- **What practitioners do:** ralphctl's cost-tiered presets + stall-driven model-ladder escalation carrying critique upward; DeepClaude's 80/20 routine/frontier heuristic; McCabe's "run local to keep it free."
- **What datawatch lacks:** a feedback term in selection. BL6 measures spend, BL20 routes by keyword/config order, ComputeNode failover is a static priority list — `routing_rules_test` exists, `routing_rules_optimize` does not; nothing re-routes on measured quality, and nothing escalates a stalled task to the next model rung.
- **Differentiation:** this is `feature-themes.md` theme 6 verbatim; no enhancement-proposals.md entry claims it yet. Its inputs (sweep results from proposal #1, verdict history from #2) make it explicitly *after* proposals 1+2 in the sequencing.

### 3. No mid-run model swap (pattern 7)

- **What practitioners do:** DeepClaude's `/_proxy/mode` slash-command backend flip with context carried; Eve's auto-router escalating "real coding work" to the cloud model mid-conversation; ralphctl's mid-run ladder climb.
- **What datawatch lacks:** the swap grain. Registry failover and `compute_node_pull_model` make a downed model survivable, and per-task overrides make the *next* task cheaper — but a running tmux session cannot have its backend flipped; the only "swap" is `restart_session` with a new `task` string, which does not carry the live session's conversational state.
- **Differentiation:** not covered by `enhancement-proposals.md`. It composes with gap #2: the stall-triggered escalation (ralphctl) is "swap on a detected condition," which needs the audit artifact from gap #1 to even detect the stall.

### 4. Per-action human gating delegated, not owned (pattern 2)

- **What practitioners do:** Storer/pcollins per-tool allow/deny in the loop; Niptao's `go/skip` reply as the gate; albert-ying's `autolab_editorial` accept/revise/reject pause — a protocol step the operator must take to proceed.
- **What datawatch lacks:** an in-loop, per-action datawatch-owned gate. The datawatch gates are real but coarser — plan approve/reject (BL24/BL191), guardrail-verdict approve (`session_guardrail_approve`), guided mode checkpoints — all at artifact or story boundaries; mid-run "this tool call, allow or deny?" is delegated to claude-code `permission_mode` / backend sandbox behavior, which the operator cannot query or tune per-action from the datawatch surface.
- **Differentiation:** partially mitigated by BL369 `block_on_injection` (a hard gate at the spec boundary) and by `enhancement-proposals.md` #5 (red-team validator pipeline), which adds a new gate at the PRD/task boundary; neither touches the per-tool-call granularity, which is where the practitioner gap sits.

### 5. Warn-only injection depth at the model boundary (pattern 5)

- **What practitioners do:** Niptao's injection guardrail over all in-band content as a *block* ("never obeyed"); Verma's "assume the model will fumble, and build the catch"; Quorum's hardware-aware scheduling (VRAM) as a guardrail; Featherbench's canary negative controls.
- **What datawatch lacks:** enforcement depth beyond the phrase scan. BL369 is literally flagged "currently warn-only" in the baseline task description; `CheckInjectionGuard` is a lexical detector, not a multi-stage validator pipeline, and there is no obfuscation-resistant (LVM-judged) stage, no canary-string negative control, no hardware-aware scheduling tier (Quorum's "models auto-run sequentially" has no datawatch analogue — ComputeNode failover is node-level, not VRAM-contention-level).
- **Differentiation:** `enhancement-proposals.md` #5 (red-team validator pipeline) is precisely this delta's implementation proposal — recorded here only to note (a) it is not yet in the proposals doc's sequencing above themes 1+2, and (b) Quorum's hardware-aware tier and Featherbench's canaries are *outside* proposal #5's scope and would be separate additions to the guardrail library.

### 6. No suite×backend comparison surface (pattern 11)

- **What practitioners do:** Featherbench's pinned 28-task panel re-run at every model release ("any score movement is provably the model's"); McCabe's 58-case golden set with frontier-model swap-in.
- **What datawatch lacks:** the comparison. BL259 re-runs a suite fine (single-variable discipline honored), but choosing between two backends means running the suite twice by hand and eyeballing two `Run` rows — no side-by-side, no normalized cost/latency column, and the DAG cannot gate on the result.
- **Differentiation:** fully owned by `enhancement-proposals.md` #1 (eval sweep matrix + `RunSet`) and #2 (eval node kind in BL117). Zero new delta to add; this row exists so the mapping table's PARTIAL rating has a home in the gap ranking, and so any future proposal can cite that this gap is *claimed, not open*.

## Coverage summary

- **MATCH:** 6/12 patterns — memory (#1), lineage/rollback (#4), guardrail chains (#5), verifier (#6), fresh-context (#9), DAG (#10). Every one of these matches is already named as a datawatch differentiator in `synthesis.md`; this pass confirms the practitioner catalog converged on the same axes independently.
- **PARTIAL:** 5/12 — HITL gate (#2), cost routing (#3), mid-run swap (#7), eval sweep (#11), council method selection (#12). Four of five have prior claims in `feature-themes.md`/`enhancement-proposals.md`; the council-method one (#12) is genuinely new and small.
- **MISSING:** 1/12 — per-LLM-call audit (#8). This is the only gap no prior doc claims, and it is also the dependency the other gaps (route-on-quality, mid-run swap, eval-sweep cost tables, lineage export) all implicitly require.
