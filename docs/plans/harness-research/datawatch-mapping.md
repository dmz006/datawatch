Ratings:

- **MATCH** — datawatch implements the pattern as a first-class surface (package, API, config, or BL).

## Gaps ranked by practitioner frequency and blast radius

Ordered by (a) how many pattern rows and distinct builders touch the delta, and (b) how load-bearing the missing primitive is to other proposed features.

### 1. No per-LLM-call request/response artifact (patterns 7, 3, 6, 13, 16)

- **What practitioners do:** Storer's inspectable LLM transactions ("assembled system prompt, tool schemas, input messages, output blocks, token/cache use, stop reason"), Verma's ref registry, joacod's "every provider call is a first-class event on the run," Featherbench's "raw JSONL published so anyone can re-score," McCabe's "identical token counts across different prompt runs exposed that the version flag was never threaded through."
- **What datawatch lacks:** the exact-call record. `internal/inference/dispatcher.go:37-59` ships `Request`/`Response` as *ephemeral* transport types; neither is persisted anywhere. `internal/audit/` (BL9) logs *operator* events; `telemetry_get` and `session_timeline` log *task/verdict state*; `observer_stats` envelopes log *process-level* CPU/mem/net per session and per-LLM-backend (the eBPF view); BL6 `cost_usage` logs *token totals per session* — but no surface can answer "what was the 7th prompt in session X, verbatim, what tools did the model call, and what did it say back?"
- **Why it blocks more than the obvious:** the route-on-quality surface (Gap #2), the eval-sweep cost/latency table (`enhancement-proposals.md` #1), and the lineage export (#3) all need the per-call span as a *primitive*. The daemon already does `observer_stats` at the process envelope level; the span is the next granularity. `callRecord` exists in `internal/inference/dispatcher_test.go` as a test helper only — confirming the primitive is not on the ship path.
- **Differentiation:** `enhancement-proposals.md` #3 (unified lineage query + OpenInference export) assumes the span primitive exists; this gap is what has to land first for #3, #1, and any quality-routing work to be trustworthy.

### 2. Cost and quality not wired into routing decisions; no stall-triggered model-ladder escalation (patterns 6, 14, 16, 18)

- **What practitioners do:** ralphctl's cost-tiered presets + "climbs the ladder one rung at a time on a stall, carrying the critique"; DeepClaude's 80/20 routine/frontier heuristic with live switching; McCabe's "run local to keep it free"; Quorum's VRAM-aware sequential scheduling.
- **What datawatch lacks:** a feedback term in selection. BL6 measures spend (BL6 `/api/cost`, per-backend USD rate table, per-session token counters) — it is *observation only*; nothing re-routes on measured cost or quality. `internal/inference/dispatcher.go:120` walks `llm.ComputeNodes` in fixed priority order and returns the first working one; `llm.max_inflight` and `compute_node.max_concurrent_sessions` are session caps, not VRAM-contention locks. There is no "on `ErrWorkerStalled`, climb one level on the model ladder carrying the critique" surface; the executor today retries the *same* model bounded by `auto_fix_retries` (BL24).
- **Why it matters:** the 80/20 split #5 DeepClaude measured is real and the daemon's static tiering (per-task/per-story/per-PRD override) *encodes* the operator's 80/20 choice but does not *decide* it. The operator has to hand-tune every task. The daemon already knows which model just failed (via `telemetry_get`), which model has been cheap lately (via BL6), and which nodes are currently under VRAM pressure (via `observer_stats`) — the routing decision is one line away from a feedback loop.
- **Differentiation:** `feature-themes.md` theme 6 verbatim. Not in `enhancement-proposals.md`. It composes with Gap #1 (need the audit artifact to *detect* the stall) and with Gap #3 (VRAM-aware scheduling needs `observer_stats` GPU data as a selection term).

### 3. No mid-run model swap (pattern 6, plus row 7)

- **What practitioners do:** DeepClaude's `/_proxy/mode` live model switch across providers (`_proxy/cost`, "without restarting the session") — the operator can flip between DeepSeek, OpenRouter, Fireworks, and Anthropic mid-conversation, context carried; Eve's auto-router escalating "real coding work" to the cloud model mid-conversation; ralphctl's mid-run ladder climb.
- **What datawatch lacks:** the swap grain. A *running* tmux session cannot have its backend flipped; the only "swap" is `restart_session` with a new `task` string, which kills the live session and loses conversational state. The session manager's `Restart`/`RestartSession` (internal/session/manager.go:3155, 3364) kills then relaunches — that is not DeepClaude's `/_proxy/mode` (which preserves context and token cache). Registry failover (`internal/inference/dispatcher.go:120` walk) is at the *call* level for *new* calls; not for the *live session*.
- **Why it matters:** in datawatch's actual architecture, the *session* is the unit of work (tmux pane), not the *call*. The dispatcher's "swap" is transparent to the session, which is the right boundary for the daemon (a session is a long-lived tmux process with its own token cache, tool state, and memory context) — but it means the DeepClaude pattern is a *different feature* datawatch has not shipped: the operator can flip the *next* turn's model cheaply, not the *running* turn's. `llm_test` + `llm_enable/disable` + `pretest` is the closest probe surface, but it is at the registry level, not at the live-session level.
- **Differentiation:** Not covered by `enhancement-proposals.md`. Composes with Gap #2 (stall-triggered escalation = swap on a detected condition, which needs the audit artifact from Gap #1 to detect the stall and the session-level backend flip to act on it).

### 4. Per-action gating delegated to the underlying harness, not owned; injection guard is warning-depth today (patterns 4, 8)

- **What practitioners do:** Storer/pcollins per-tool allow/deny in the loop ("permission is per-action, not per-session"); Niptao's `go/skip` reply as the gate; albert-ying's `autolab_editorial` accept/revise/reject pause; Forcefield's three-state allow/ask/deny "evaluated before execution"; Quorum's VRAM contention lock.
- **What datawatch lacks:** an in-loop, per-action datawatch-owned gate. The datawatch gates are real but coarser — plan approve/reject (BL24/BL191 `autonomous_prd_approve/reject/request_revision`), guardrail-verdict approve (`session_guardrail_approve`), BL367 regression blocking (`quality_gates_block_on_regression`), `autonomous_prd_set_guided_mode` (per-story checkpoint), `autonomous_config.block_on_injection` (spec-boundary only, off by default — the hard block exists, but the detector is lexical at ~11 regexes, `internal/autonomous/security.go`) — all at artifact or story boundaries. The mid-run "this tool call, allow or deny?" is delegated to the backend's own permission mode (claude-code `permission_mode: default | plan | acceptEdits | auto | bypassPermissions | dontAsk`; opencode sandbox), which the operator can tune in the LLM registry (`llm_add` with `permission_mode`) but *cannot* query or tune from the datawatch surface mid-run. There is no `datawatch_tool_call_decide`-shape API.
- **Why it matters:** the daemon's trust boundary is the *container/k8s* boundary (F10 agents) or the *harness* boundary (a tmux pane running claude-code), not the *datawatch* boundary. That is a reasonable split — datawatch correctly does not try to interpose on the agent's tool calls, it trusts the harness to enforce them. But it means the operator's audit of "what did the agent just try to do" is limited to (a) the session output, (b) the harness's own logs (`session_output`), (c) the daemon's audit log (BL9), and (d) the eBPF envelopes (`observer_stats`) — four surfaces that the operator has to correlate by hand, with no in-loop "I just vetoed tool X" event the daemon can query.
- **Differentiation:** partially mitigated by BL369 `block_on_injection` (a hard gate at the spec boundary) and by `enhancement-proposals.md` #5 (red-team validator pipeline), which adds a new gate at the PRD/task boundary. Neither touches the per-tool-call granularity, which is where the practitioner gap sits.

### 5. No hardware-aware (VRAM-contention) scheduling surface (patterns 8, 10)

- **What practitioners do:** Quorum's Ollama models "run sequentially to prevent VRAM contention"; Eve's local persona models with byte-exact KV-prefix caching; Forcefield's local-first design.
- **What datawatch lacks:** a VRAM-contention lock. `compute_node.max_concurrent_sessions` is a *session* cap, not a VRAM lock; `llm.max_inflight` is a *call* cap; the capacity ledger (`internal/capacity/ledger.go`) pools on `host`, `node:<name>`, and `llm:<name>` — three pools, none of which are VRAM-aware. The GPU is visible (`observer_stats.gpu`, `compute_node.gpu_mem_gb`) but nothing in `internal/inference/dispatcher.go`, `internal/capacity/ledger.go`, or `internal/autonomous/executor.go` makes a routing/scheduling decision from it. Two concurrent Ollama calls on the same node with a 13B and a 27B model can double-book VRAM and either OOM or thrash the swap.
- **Why it matters:** the local-inference tier is datawatch's strongest differentiator vs "just use the cloud" (row 10, row 6), and a VRAM-contention lock is the one primitive that makes two local models usable at the same time — the "two-model debate" pattern in row 18 degrades to "sequential, not parallel" on a local node today. A `compute_node.gpu_mem_gb` + `observer_stats.gpu` + a per-LLM `VRAM_reserve` field would close it.
- **Differentiation:** not covered by `enhancement-proposals.md` or `feature-themes.md`. Composes with Gap #2 (the routing decision needs the GPU data as a selection term).
