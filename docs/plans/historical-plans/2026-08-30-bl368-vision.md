### Phase 2 — Comms router ✅ Done (v8.15.0)

- `Attachment.IsImage()` in `internal/messaging/backend.go`
- `Visioner` interface + `SetVisioner()` in router
- Image attachment block in `processMessage`: read file → `Describe()` → prepend `[image: <desc>]` to `msg.Text`

- Wired into all routers (Signal, Telegram, test router) + HTTP server in `main.go`

### Phase 3 — MCP tool + session injection ✅ Done (pending release)

- `vision_describe` MCP tool: `vision_describe(image_path, prompt)` — reads file, calls `VisionerMCP.Describe()`, returns description
- `image_paths: string[]` on `start_session` — descriptions prepended to task before session spawn
- `image_paths: string[]` on `send_input` — descriptions prepended to text before delivery
- `VisionerMCP` interface + `SetVisioner()` on MCP `Server` struct
- `buildImagePrefix()` helper handles multi-image numbering and error resilience
- `visionExtMIME()` helper for extension→MIME mapping
- Wired in `main.go`: primary MCP server + Goose channel MCP server
- `docs/mcp.md` updated: `vision_describe` tool definition, `image_paths` in `start_session` + `send_input` tables, Vision family row in tool table

### Phase 4 — Skills + memory + council ✅ Done (pending release)

- `AcceptsImages bool` field added to `internal/skills/manifest.go` `Manifest` struct; YAML tag `accepts_images`; skills that accept image context declare it in SKILL.md frontmatter
- `remember [image]` via comms: router image-injection block is now command-aware — when original message starts with `remember:`, image description is injected INTO the command body (`remember: [image: <desc>] <caption>`) so `handleRemember` receives the full text and stores it in episodic memory
- Council `image_path` parameter: `POST /api/council/run` now accepts `image_path`; if set and `s.visioner` is wired, the file is read, described, and `[image: <desc>]` is prepended to `proposal` before it reaches `Run()` / `StartAsync()` / `StartAsyncWithOptions()`
- PRD decompose `image_context`: deferred — `DecomposeStreaming` interface needs a context parameter; tracked as follow-up in BL368 backlog
- Alert `chart_path` + BL366 verifier screenshot: deferred to a dedicated sprint alongside BL366

## Config reference

```yaml
vision:
  enabled: false
  backend: ollama          # "ollama" | "openai" | "openai_compat"
  endpoint: http://localhost:11434
  api_key: ""              # optional; required for upstream OpenAI
  model: llava             # must be vision-capable; no auto-detection
  default_prompt: ""       # defaults to "Describe this image concisely."
  max_image_bytes: 0       # 0 = 10 MB default
```

## Supported models

| Backend | Models |
|---|---|
| ollama | llava, llava-phi3, llava-llama3, bakllava, moondream, minicpm-v |
| openai | gpt-4o, gpt-4-vision-preview |
| openai_compat | any model served via an OpenAI-compatible endpoint |
