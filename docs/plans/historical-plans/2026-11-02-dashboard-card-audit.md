# Dashboard card audit — Mission Control

**Date:** 2026-11-02
**Version:** none (audit record; plan-document commits are exempt from the version bump)
**Tracker:** row for the dashboard card audit and operator console in `docs/plans/README.md`

**Design basis:** the operator's 2026-11-01 answer to "what the dashboard is for" — *console first, boards later*: "We already have the observer, we don't need to replicate what is there in boards, but boards for a dashboard are different and higher level, some observer cards may be good dashboard cards" (verbatim answer, with the other questions, in the answers table of `docs/plans/2026-10-29-pre-10-0-design-proposals-index.md`, read 2026-11-01 14:30). The audit therefore judges every card against the console question "do I need to do anything and is anything stuck?", per the proposed first step in `docs/plans/2026-10-30-dashboard-purpose-proposal.md`: record each card's data source, whether it is empty on a normal installation and why, who would act on it; remove or hide a card with no data source on a normal installation; a card with nothing to show says why in one line and links to the setting that fills it.

## Scope

This record audits every dashboard card that Mission Control (the `/dashboard` view) renders, from the card library `DASH_CARD_DEFS` and the default layout `DASH_DEFAULT_LAYOUT` in `internal/server/web/app.js` (the "BL303 S5 — Dashboard Card Grid" section, around lines 37492 to 37540), the fetchers and renderers called from `_dashBuildGrid` and the `_dashLoop` rAF cycle in the same file, and the Go factory defaults `defaultDashCards`, `mergeSystemCards`, `readDashLayout` and `writeDashLayout` in `internal/server/api_dashboard_cards.go`. Cards covered: `tree` (label Automata), `orbital` (label Network), `events`, `sparklines`, `gantt`, `heatmap`, `guardrails`, `ekg`, `smoke`, `memory-scope`, `websearch-usage`, and `integration-status`. Also audited: how `tree` can appear twice in the stored layout, and the `websearch-usage` mismatch between the PWA defaults and the Go defaults. This task changes only this audit record; no code, config or layout file is edited. "Normal installation" means: no schedules, no web search providers, no smoke runs, no memory scopes, no observer peers and no sessions.

## Duplicate Automata card

Observed (already noted in `docs/plans/2026-10-30-dashboard-purpose-proposal.md`: "The stored layout also lists the Automata tree twice"): the stored layout `~/.datawatch/dashboard-layout.json` contains the card id `tree` twice, so `_dashBuildGrid` renders two Automata cards, each creating a second `dashTree` element.

Trace, all in `internal/server/api_dashboard_cards.go` unless noted:

1. **Write.** `writeDashLayout` serialises whatever card array it is given to `dashboard-layout.json` with no validation, no de-duplication, no id uniqueness check. Nothing in this file ever asserts that ids are unique.
2. **Read.** `readDashLayout` unmarshals the file and runs `mergeSystemCards`, which builds a `present` map from `cards[]` and re-appends only *missing* system cards (`for _, d := range defaults { if !present[d.ID] … }`). Because `present` is a `map[string]bool`, an id already present twice counts as present, so `mergeSystemCards` **cannot remove an existing duplicate** — it can stamp `System=true` onto both copies but never collapses them. Its only job is re-adding cards a PUT or manual edit removed.
3. **Append entry point without a uniqueness guard.** `dashCardsAddHandler` (`POST /api/dashboard/cards`) does `layout.Cards = append(layout.Cards, card)` after only checking that `card.ID != ""` — there is no "is this id already in the layout?" check, unlike the update handler's upsert which searches by id. A duplicate `tree` can therefore enter the file this way (a client POST, or any caller of the cards API that appends rather than upserts). The PWA side matches this asymmetry: `window._dashAddCard` in `internal/server/web/app.js` guards *plugin* widget ids with `if (_dash._layout.some(c => c.id === cardId)) return;` but pushes *built-in* ids with no such guard; the Add-Card panel currently hides the click for already-used definitions, so the client can reach the unguarded path through any other caller or a stale/edited layout.
4. **Replace path preserves duplicates.** `handleDashboardLayout` in `internal/server/api_dashboard_layout.go` (PUT `/api/dashboard/layout`, written by `_dashSaveLayout`) replaces the stored layout *wholesale*: it decodes the client's full `cards` array, runs `mergeSystemCards(incoming.Cards)` — which, per point 2, keeps any id that is already present, however many times — and calls `writeDashLayout`. So once `tree` is duplicated in `_dash._layout` on a client (loaded there by `GET /api/dashboard/layout`, point 2), every subsequent edit save writes both copies back and re-stamps both `System:true`.
5. **Delete cannot repair it.** `dashCardDeleteHandler` returns `409 "cannot delete system card"` for the first matching entry it sees; `mergeSystemCards` (point 2) has stamped `System=true` on *every* `tree` entry, so removing either copy through the REST API is refused, and only the PWA's in-memory `filter` removes both entries at once and its next save writes the healed list — so the asymmetry is concrete: the REST delete path is locked out of repairing the duplicate while the PWA path is not, and there is no code path that repairs it for you).

**Cause, stated:** the stored layout has no id-uniqueness invariant anywhere — the two writers that can add an id (`dashCardsAddHandler`'s unguarded append, and the PWA's unguarded built-in push) admit a second `tree`, and the one shared normaliser that all paths run through, `mergeSystemCards`, is designed only to *add missing* system cards (its `present` map treats "present at least once" as done), so the duplicate survives every read, survives every PUT replacement (which is wholesale and inherits the client's duplicate), and the system-card protection that is meant to prevent deletion instead locks both copies in place. Fix direction for the console PRD (not acted on here): validate unique ids at write time in `writeDashLayout`/handlers, de-dup by first-occurrence in `mergeSystemCards`, and heal one existing `~/.datawatch/dashboard-layout.json` file.

## Decisions

Per card (id in backticks), applying the operator's 2026-11-01 design basis (console first; "some observer cards may be good dashboard cards") and the purpose proposal's test — *a card with nothing to show says why in one line and links to the setting that fills it*:

- `tree` — **keep** as a system card; it is the automata console itself (PRD progress, held/blocked work, active sessions).
- `orbital` — **keep** but demote: a one-line "no sessions" state with a link to start one; revisit once the console ranks cards.
- `events` — **keep**; the live "anything stuck" feed, core console.
- `sparklines` — **keep** tentatively; overlaps `ekg` and `events`, candidate to fold into the console summary rather than a standalone card.
- `gantt` — **keep**; the project time view the operator asked for (which Automata are held, blocked, waiting for a merge).
- `heatmap` — **keep**; answers 30-day activity/usage rhythm at negligible cost.
- `guardrails` — **hide unless the guardrails feature is on / is producing verdicts**; remove from the default layout in that case.
- `ekg` — **keep**, and promote its burn-rate side panel because Claude usage against the pace line is an explicit console question.
- `smoke` — **hide unless its feature is on** (no runs on a normal installation; developer-only artifact) — out of both default layouts, remain addable.
- `memory-scope` — **hide unless its feature is on** (no scopes on a normal installation).
- `websearch-usage` — **hide unless web search is enabled**; additionally align the two defaults (see below) with Go as the canonical list.
- `integration-status` — **keep as opt-in** (it is already not in `DASH_DEFAULT_LAYOUT`; the comment in `DASH_CARD_DEFS` says it is deliberately excluded); the pattern to copy.

Consistency rule the console PRD should encode: default layouts ship only cards with a data source on any working installation; subsystem tiles are addable and self-declare their empty reason with a link to the setting, exactly as `integration-status`/`smoke` already do. And the id-uniqueness invariant in `writeDashLayout`/`mergeSystemCards` (Duplicate Automata card section) so the layout file can never hold `tree` twice again.

Audit-only task: **no behaviour changes yet** — each surface below states the planned change (the console PRD implements it) or why it is excluded from any change in this round.

- **REST** — the dashboard layout routes (`GET`/`PUT /api/dashboard/layout`, `/api/dashboard/cards*` in `internal/server/api_dashboard_cards.go` / `api_dashboard_layout.go`) are read today, unchanged; planned: unique-id validation and de-dup at write time, system-card list made the sole source of the default set. Excluded now: nothing ships.
- **MCP** — no dashboard-card tool reads or writes the layout in this audit; planned: none specific, unless the operator console exposes card state for tooling. Excluded: no behaviour change.
- **CLI** — CLI consumers of the dashboard cards API (list/set) are untouched; planned: nothing beyond the same server-side de-dup appearing for free. Excluded: no new commands in this round.
- **Comm channel** — session-to-session/peer traffic is not a layout source; planned: none. Excluded: the layout is per-installation state, not federation traffic.
- **YAML/config** — no YAML key drives card defaults today (the defaults are code constants in `internal/server/web/app.js` and `internal/server/api_dashboard_cards.go`); planned: a config switch for feature tiles if we make "hide unless its feature is on" operator-selectable, with the audit's decision as default. Excluded now: no new key added.
- **PWA** — the audited surface; planned: drop `smoke`/`memory-scope`/`websearch-usage` from `DASH_DEFAULT_LAYOUT`, guard the `_dashAddCard` built-in path, one-line empty states with setting links. Excluded now: no JS edited.
- **Android** — no native dashboard; it renders the PWA; planned: inherits the PWA changes. Excluded: nothing Android-specific.
- **iPhone/iOS** — same as Android: PWA-based, inherits the planned changes; excluded from any direct change in this round.
