## Decision Log

| # | Decision | Rationale |
|---|---|---|
| D1 | Resources = pull context only; no subscriptions in v7.1.0 | Claude Code has no built-in behavior on resource update notifications; subscriptions go in v7.2.0 after we observe usage |
| D2 | Resource URI scheme: `datawatch://` | Clean namespace; channel bridge already forwards all MCP calls via REST proxy |
| D3 | Sampling included in v7.1.0, alongside elicitation | Both are daemon-initiated; share plumbing; build once |
| D4 | Elicitation alongside sampling but does NOT replace permission relay | Relay has proven semantics and deployed clients; replace in v7.2.0 |
| D5 | Prompts reduced to 10 focused slash commands | Sampling covers daemon-initiated flows; prompts cover operator-initiated |
| D6 | Plugin/skill manifest declares sampling triggers | Plugins can request Claude analysis as part of their lifecycle |
| D7 | Tool annotations added (readOnly/destructive) on all existing tools | Low effort; Claude Code uses annotations for permission UX |
| D8 | Council sampling: daemon includes Claude Code as deliberation member | Natural fit with Council architecture; wired in S3 |
| D9 | No subscriptions, no roots, no completions in v7.1.0 | Deferred to v7.2.0 after seeing how clients use the read surface |

#### Resource content format

Each handler returns `mcpsdk.TextResourceContents` with JSON content for structured data, or `mcpsdk.TextResourceContents` with Markdown for docs. MIME types:
- JSON resources: `application/json`
- Docs: `text/markdown`

#### Live handler pattern

Each live handler calls the same internal data sources the REST API uses, not the REST API itself (avoids loopback HTTP overhead):

```go
func (s *MCPResourceServer) handleSessionsResource(ctx context.Context, req mcpsdk.ReadResourceRequest) ([]mcpsdk.ResourceContents, error) {
    sessions := s.sessionStore.ListActive()
    data, _ := json.Marshal(sessions)
    return []mcpsdk.ResourceContents{
        mcpsdk.TextResourceContents{URI: req.Params.URI, MIMEType: "application/json", Text: string(data)},
    }, nil
}
```

#### Task 3.1 — Sampling infrastructure

**File**: `internal/mcp/sampling.go` (new)

```go
type SamplingDispatcher struct {
    srv    *server.MCPServer
    stats  *MCPStatsBlock
}

func (d *SamplingDispatcher) Sample(ctx context.Context, req SamplingRequest) (*SamplingResult, error)

type SamplingRequest struct {
    Trigger    string                // "alert_triage", "anomaly", "briefing", "council", "automaton"
    Messages   []SamplingMessage     // conversation history to send
    SystemPrompt string             // optional system context
    MaxTokens  int                  // default 1024
}
```

Calls `d.srv.RequestSampling(ctx, mcpsdk.CreateMessageRequest{...})`. If no client connected (`ErrSamplingNotSupported`), returns error gracefully — callers degrade to local LLM call.

Result saved to sampling log (ring buffer, last 50 entries) accessible at `datawatch://stats/mcp`.

```go
    Prompt     string `yaml:"prompt"`      // template with {{.Output}}, {{.Error}}, etc.
    MaxTokens  int    `yaml:"max_tokens"`  // default 512
}
```

Plugin lifecycle hooks check for declared triggers and fire `SamplingDispatcher.Sample()` when the event matches.

Example in a plugin's `manifest.yaml`:
```yaml
sampling_triggers:
  - event: on_complete
    prompt: "Plugin {{.Name}} completed with output: {{.Output}}. Summarize key findings."
    max_tokens: 256
  - event: on_error
    prompt: "Plugin {{.Name}} failed: {{.Error}}. Diagnose and suggest remediation."
```

#### Task 3.14–3.15 — Channel bridge: sampling + elicitation

**File**: `cmd/datawatch-channel/main.go`

At startup after `bridge.mcpSrv.EnableSampling()`:

The channel bridge is the *client* end for sampling — it's Claude Code's proxy. The daemon sends `sampling/createMessage` via the MCP connection; the channel bridge receives it and forwards to Claude Code's stdio session.

No additional code needed in the bridge itself — `server.NewStdioServer` handles the `sampling/createMessage` request/response roundtrip via the underlying mcp-go session. The bridge just needs `mcpSrv.EnableSampling()` called so it advertises the capability.

For elicitation: same pattern — the SDK's stdio server handles `elicitation/create` requests automatically once the capability is declared.

```go
func (s *MCPPromptServer) handleAnalyzeSession(ctx context.Context, req mcpsdk.GetPromptRequest) (*mcpsdk.GetPromptResult, error) {

            }},
        },
    }, nil
}
```

## Architecture Notes

### How sampling flows

```
daemon (trigger fires)
  → SamplingDispatcher.Sample(req)
    → srv.RequestSampling(ctx, CreateMessageRequest)
      → active stdio session (Claude Code)
        → Claude processes messages
        → returns CreateMessageResult
      ← result
    ← SamplingResult
  ← caller acts on result (log / route to comm / update automaton state)
```

If no Claude Code session is connected: `ErrSamplingNotSupported` returned. Caller falls back to direct Ollama/API call. Sampling is always additive, never blocking.

### How elicitation flows

```
daemon (decision point reached)
  → ElicitationDispatcher.Elicit(req)
    → srv.RequestElicitation(ctx, ElicitationRequest{Schema: "approval", ...})
      → Claude Code presents structured input to operator
        → operator responds
      ← ElicitationResult{action: "approve", note: "..."}
    ← ElicitationResult
  ← automaton/plugin continues with operator's decision
```

If no session or client doesn't support elicitation: falls back to channel notification (existing relay path).
