## Rule from now on

New PRDs are put into an Automation before they run: the supervisor approves the PRD, creates or extends an Automation with it as a member, and activates the Automation; the coordinator starts and advances the member. A PRD that is already running is not adopted until a cheap PRD has tested adoption.

## 2026-11-03 findings

1. **Planning follows the global planning backend, not the Automaton's backend.** Setting the worker backend on a draft did not move its decompose off Claude. With `planning_backend: claude-code` and a Claude cap of 1, decomposes ran one at a time and held the only Claude slot, so six drafts queued for over an hour. Fix: the planning backend and model per Automaton must be settable and shown next to the worker backend, and the capacity view must say which pool a decompose takes. Test planning on the local model pool and compare with the decompose lint scorecard before changing the global setting.
   - **Addressed — 2026-11-03, queued requeue (next patch above main).** The planning backend and model are settable per Automaton (`decomposition_profile` / `decomposition_model` on the PRD, `planning_backend` / `planning_model` on the Automation, beside the worker pair) and the capacity view names the pool a decompose takes: the wait reason says which pool the run is currently waiting for, and a queued run follows the profile you change it to — see #7.
2. **Lane fill (shadow mode) marks drafts `proposal_missing`** when the spec names no readable proposal file. Drafts filed from chat have none, so lane fill would never decompose them even in on mode. Fix: either file a short proposal document with every new draft, or let the spec itself count as the proposal; the supervisor now names a plan document in each new spec.
3. **Lane fill is still in shadow mode.** It records decisions and starts nothing, so lanes are filled by the supervisor ticks. Switching it on is a pre-10.0 step, after the proposal rule above is settled.
4. **The Automation progress view is empty until members run**, so the release arc shows zeros. The arc needs a planned view (counts of members by stage and state) before activation.
5. **An Automation whose entry member is a fork or a nested Automation cannot be activated.** Activation reads the entry as an Automaton, so it reports "next member is missing" and leaves the Automation blocked, with no route back to draft. The release arc was built as nested stages and could not start. Worked around by giving each stage an Automaton as its entry member and activating stages directly; the defect is filed in the bugs stage at priority 85.
6. **A held auto-fix task retried with an explicit backend still waits on the local pool.** `resolve-review --action retry --backend claude-code --model sonnet` set the task record to the cloud backend, but admission used the verifier policy order (local pool first), so the task waited over an hour on full local nodes while the cloud lane was idle. It was the only thing blocking a merge. Filed as a bugs-stage defect at priority 85.
7. **A planning run already queued on the local pool cannot be re-routed.** Changing an Automaton's decomposition profile to the cloud backend, restarting the decompose, and resetting it to draft (refused while planning) all left the run waiting on the full local pool, while the cloud lane sat idle. Fix to file: changing the planning backend of a queued planning run should cancel and re-queue it on the new pool, and the wait reason should show the pool of the current profile. Until then, set the planning profile before the first decompose.
   - **Addressed — 2026-11-03, queued requeue (next patch above main).** Changing `decomposition_profile` / `decomposition_model` with `set_llm` while the planning run is still queued retargets that run's single queue entry in place to the pool the current profile resolves to (outcome `requeued`; the wait reason now names the current pool), and re-calling `decompose` while the run is queued re-queues it on the current pool instead of starting a second run. A run that already started is left alone (`deferred_to_next_run`) — wait for it or cancel it. No retry-budget consumption, no leaked capacity, wait budget not reset. See `docs/howto/autonomous-planning.md` ("Changing the planning backend while planning") and `docs/operations.md` ("Planning requeue").
