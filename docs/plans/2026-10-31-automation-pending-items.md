# Automation pending items: plan record

**Date:** 2026-10-31
**Version:** next minor above main (the merge helper sets the number at merge time)
**Supersedes nothing.** The earlier proposal, `docs/plans/2026-10-28-automation-pending-item-member-proposal.md`, is left as it was written; this record holds what was decided and what was built.

## Problem

An Automation member had to be an existing Automaton. Work that has been named but not yet specified (a design still open, a request waiting on an answer) could not be placed in an Automation, so the order of that work lived only in the operator's head or in a document. The Automation could not stop at that point and wait.

## Operator decisions

- **Option C was chosen.** The proposal offered three options: a new member kind for work with no Automaton yet (A), filing a draft Automaton from the item (B), or both (C). The operator answered "C". Option A, the pending item member, is built here. Option B, filing a draft Automaton from an item, needs no new member kind: the operator creates the Automaton as usual and attaches it to the item.
- **The hold is the default.** A waiting pending item holds its Automation at the cursor until an Automaton is attached. The Automation becomes blocked, the reason names the item, and every member after it stays behind it. The hold is not an error. The policy `hold` is the default; `skip` lets the Automation pass over a waiting item and leaves the item waiting. A timer that skips an item by itself was not chosen.
- **The internal registry is the source of truth, and a file registry is one input.** Pending items live in a registry the daemon owns, a JSON file in the Automaton store directory. Nothing is read from a document at run time. The operator may point the daemon at a pipe table in a file they keep; its rows are copied into the registry as items with source `file`. The daemon only reads that file and never writes to it. It is read when the daemon starts and when the operator asks for a refresh.
- **Everything is configurable, with the operator's answers as the defaults.** Nothing may assume a numbering sequence, a file name or this repository's conventions. The id pattern, the columns, the words that mean done and what happens to a vanished row are all settings. The defaults are the operator's answers: hold, auto-resume on, no file registry.
- **Getting items moving and closed.** An item is attached to an Automaton (the attach action on every surface). The member then becomes an ordinary Automaton member in place, keeping the item as a note of where it came from. When the attached Automaton completes, the item moves to done. A file row whose state column holds a done word also moves its item to done.

## What was built

- **Data model.** A pending item has `id` (8 hex characters, generated by the daemon), `ref` (optional external label), `title`, `state` (`waiting`, `attached` or `done`), `source` (`internal` or `file`), `automaton_id` (set on attach) and the times it was created, updated, attached and finished. A new member kind, `pending_item`, carries the item id and no Automaton id.
- **The hold.** The coordinator holds the cursor on a waiting item under the `hold` policy and passes over it under `skip`. A restart keeps the hold. A done item releases it.
- **Attach.** Attaching converts every member that carries the item into an ordinary Automaton member, in place, with the same position, edges and status. With auto-resume on, an Automation that was blocked on the member resumes. Attach is refused for an item that is not waiting, an Automaton that does not exist, one that another Automation or item already owns, and a template or child Automaton.
- **The file registry.** A reader for a pipe table with a configurable id pattern, id column, title column, optional state column and done words, and a refresh that is safe to repeat. An unreadable file leaves the registry as it was. A path that escapes its allowed directory is refused.
- **The nine settings**, all under `autonomous.automation`: `pending_item_policy`, `pending_item_auto_resume`, `pending_item_source.path`, `pending_item_source.id_pattern`, `pending_item_source.id_column`, `pending_item_source.title_column`, `pending_item_source.state_column`, `pending_item_source.done_values` and `pending_item_source.on_missing_row`. A column setting is a header name (matched without regard to case) or a 1-based column number.
- **The operator guide** is `docs/howto/automaton-pending-items.md`.

## Parity surface

Every surface gives the operator the same information and the same actions: read the items and the held Automations, add an item, insert an item as a member, attach an Automaton, refresh the file registry, and read and change the nine settings.

- **REST.** `GET` and `POST /api/autonomous/pending-items`, `POST /api/autonomous/pending-items/{id}/attach` and `POST /api/autonomous/pending-items/refresh`. The nine settings go through `GET` and `PUT /api/config` and `PUT /api/autonomous/config`. The insert-member route accepts a pending item id. The routes are in `docs/api/openapi.yaml`.
- **MCP.** The tools `autonomous_pending_items`, `autonomous_pending_item_add`, `autonomous_pending_item_attach` and `autonomous_pending_items_refresh`; `automation_insert_member` takes a pending item id; the nine settings are parameters of `autonomous_config_set`.
- **CLI.** `datawatch autonomous pending-items`, `pending-item-add`, `pending-item-attach` and `pending-items-refresh`; `datawatch automation insert <id> --pending-item <item-id>` inserts an item as a member; the nine settings are set with `datawatch config set`.
- **The comm channel.** (the chat channel, one `autonomous` verb per action) The verbs `autonomous pending-items`, `pending-item-add`, `pending-item-attach` and `pending-items-refresh`; the insert verb takes a pending item; the nine settings are changed with `configure`; the alert for a held Automation carries the attach hint.
- **YAML / config.** All nine keys read and write under `autonomous.automation` in the config file, with the defaults above, strict validation and an apply step that takes effect without a restart. They are listed in `docs/config-reference.yaml`.
- **PWA.** A **Pending items** card on the Overview sub-tab of the Automation screen (policy and registry lines, every item with state and ref, held Automations, an attach control, an add form and a refresh button shown only when a file registry is configured), a **Waiting for an Automaton** badge with an attach control on a pipeline member, an insert-a-pending-item field on the insert member form, and a **Pending items** group in the Automaton settings. Every string is a locale key in the five bundles.
- **Android.** Included. The datawatch-app repository gets the same information and actions; the parity issue is filed as datawatch-app issue 446 and recorded in `docs/plans/parity-issues/2026-10-31-automaton-pending-items-parity.md`. Capability parity is required; the implementation is that repository's work, not this one's.
- **iPhone.** Included, in the same issue and with the same reason: the change is a capability of the shared contract, built in the datawatch-app repository.
- **Left out: none.** No surface is skipped. The only item not built as a separate control is option B (filing a draft Automaton from an item); it needs no new surface because creating an Automaton and attaching it uses the controls above.
