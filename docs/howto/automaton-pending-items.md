# Automaton pending items

Some work is real and ordered, but nobody has written it up as an Automaton
yet. It may still wait on a design decision, or it is one line on a list. If an
Automation could only hold Automata, that work would have no place in the chain:
the Automation would run past it, or the order would live only in somebody's
head.

A **pending item** fills that gap. It is a named piece of work that has **no
Automaton yet**. An Automation can carry it as a member, in the right place in
the chain. When the chain reaches it, the Automation **holds** there and waits.
When you attach an Automaton to the item, the member turns into an ordinary
Automaton member in the same place, and the Automation carries on.

It works for any project and any list of work. Nothing in it assumes a file
name, a numbering scheme or the layout of any repository.

## What a pending item is

The daemon keeps its own registry of pending items. It is a small file in the
Automaton store directory, owned by the daemon. It is never read out of a
document you maintain: you add items through the daemon, or you point the daemon
at a table in a file you keep (see *A file registry* below) and it copies the
rows in.

| Field | Meaning |
|---|---|
| `id` | Eight hex characters, generated by the daemon |
| `ref` | Optional outside label, for example the id the work has in a list you keep. Free text |
| `title` | The name of the work |
| `state` | `waiting`, `attached` or `done` |
| `source` | `internal` (you added it) or `file` (the file registry supplied it) |
| `automaton_id` | The Automaton attached to it, once there is one |
| `created_at`, `updated_at`, `attached_at`, `done_at` | When each thing happened |

The three states:

| State | Meaning |
|---|---|
| `waiting` | The work has no Automaton yet. An Automation that reaches it holds, or skips it, depending on the policy |
| `attached` | An Automaton is attached. The Automation carries it as a normal member |
| `done` | The work is finished. It is final: a `done` item never goes back |

## Why an Automation holds

The default policy is `hold`. When the cursor of a running Automation reaches a
member that is a waiting pending item, the Automation does not start anything.
It becomes **blocked**, with a reason that names the item, for example *member
"Write the migration guide" is a pending item waiting for an Automaton to be
attached*. Every member after it stays behind it, so the order you set is the
order that holds.

The hold is not an error and it costs nothing while it waits. It ends in one of
four ways:

- **You attach an Automaton** to the item. The member becomes an Automaton
  member in place and, with auto-resume on (the default), the Automation
  resumes and starts it.
- **The item turns `done`**, because its row in the file registry says so. The
  member is passed over and the Automation moves on.
- **You skip the member** with the usual skip member action, or remove it.
- **The policy is `skip`.** The Automation never holds at a waiting item: it
  passes the member over on its normal "complete" edge and goes on. The item
  stays `waiting`.

A member whose item has vanished from the registry also holds, with a reason
that says so, because the daemon cannot tell what it was meant to wait for.

## Add a pending item

Give it a title, and a `ref` if the work already has a label somewhere else.

| Method | How |
|---|---|
| **CLI** | `datawatch autonomous pending-item-add --title "Write the migration guide" --ref guide-1` |
| **MCP** | `autonomous_pending_item_add` with `title` and optional `ref` |
| **REST API** | `POST /api/autonomous/pending-items` with `{"title": "...", "ref": "..."}`; the reply is the new item |
| **Comm channel** | `autonomous pending-item-add Write the migration guide ref=guide-1` |
| **Web UI** | Automata tab → Automation view → **Overview** sub-tab → the **Pending items** card → *Add a pending item* |

The title must not be blank. The reply carries the new item:

```
$ datawatch autonomous pending-item-add --title "Write the migration guide" --ref guide-1
Recorded pending item a1b2c3d4 (waiting): Write the migration guide [ref guide-1]
```

## Put an item in an Automation

An item becomes a member through the ordinary *insert member* action, with the
item in place of an Automaton. Give the item or an Automaton, never both, and
always a reason.

| Method | How |
|---|---|
| **CLI** | `datawatch automation insert <automation-id> --pending-item a1b2c3d4 --reason "Waits on a design decision"`; add `--after <member-id>` to place it after a member, or `--urgent` for the next slot |
| **MCP** | `automation_insert_member` with `pending_item_id` in place of the Automaton id |
| **REST API** | `POST /api/automations/{id}/insert_member` with `{"member": {"pending_item_id": "a1b2c3d4"}, "reason": "..."}` |
| **Comm channel** | `automation insert <automation-id> pending_item=a1b2c3d4 [urgent] <reason>` |
| **Web UI** | The Automation's insert member form → *Or insert a pending item (work with no Automaton yet)* |

On a draft Automation the member lands in the chain at once. On a running
Automation the insert waits for your approval (`datawatch automation approve
<automation-id> <member-id>`), exactly like an inserted Automaton.

Only a **waiting** item can be inserted, and an item can be a member of one
Automation at a time. Inserting an item that does not exist is refused with
`404:`; an item that is not waiting, or already belongs to another Automation,
with `409:`.

On the pipeline strip a pending item member carries the badge *Waiting for an
Automaton*, so a hold is easy to find.

## Attach an Automaton

When the work has been written up and decomposed into an Automaton, attach it to
the item. The Automaton must exist, must not be a template or a child of
another Automaton, and must not already belong to an Automation.

| Method | How |
|---|---|
| **CLI** | `datawatch autonomous pending-item-attach a1b2c3d4 --automaton <automaton-id>` |
| **MCP** | `autonomous_pending_item_attach` with `item_id` and `automaton_id` |
| **REST API** | `POST /api/autonomous/pending-items/{id}/attach` with `{"automaton_id": "..."}` |
| **Comm channel** | `autonomous pending-item-attach a1b2c3d4 <automaton-id>` |
| **Web UI** | The **Pending items** card → the item → *Automaton id to attach* → **Attach Automaton**; every Automation held on the item shows the same control |

What an attach does, in one step:

1. Every Automation that carries the item as a member has that member
   **converted in place** into an ordinary Automaton member for the attached
   Automaton, with the same position, the same edges and the same status. The
   member keeps the item's id as a note of where it came from. A held insert for
   the item is converted the same way.
2. The item moves from `waiting` to `attached` and records the Automaton and the
   time.
3. An Automation that was blocked on that member **resumes** and starts the
   Automaton, if auto-resume is on. With auto-resume off, the Automation stays
   blocked and the reply says so: resume it yourself when you want the Automaton
   to start.
4. When the attached Automaton later completes, the item moves from `attached` to
   `done`.

```
$ datawatch autonomous pending-item-attach a1b2c3d4 --automaton 7e41
Attached Automaton 7e41 to pending item a1b2c3d4 (attached): Write the migration guide
  converted in Automation Release train: members m4
  resumed Automation 5c20
```

Attaching a second time is refused with `409:`, because the item is no longer
waiting. An unknown Automaton is refused with `404:`.

## Reading the state

Every surface reads the same registry, and none of the reads changes anything.

```
$ datawatch autonomous pending-items
Pending items (policy: hold, auto-resume: on):
  a1b2c3d4  waiting   Write the migration guide [ref guide-1]
      held: Automation Release train waits since 2031-03-02 09:40 UTC: member "Write the migration guide" is a pending item waiting for an Automaton to be attached (item a1b2c3d4); attach one to continue
  b7c8d9e0  done      Move logs to the new disk [ref move-logs] (file)
File registry: not configured
```

The list takes an optional state (`waiting`, `attached` or `done`) and an
optional Automation id to narrow it. The reply holds the `policy` and
`auto_resume` in effect, the `source` settings and whether a file registry is
configured, `last_refresh`, the `items` (each with the Automations that carry it)
and `held`, one entry for every Automation that is waiting on an item right now,
with since when and why.

| Method | How |
|---|---|
| **CLI** | `datawatch autonomous pending-items`; narrow with `--state waiting` or `--automation <id>`; `--json` prints the raw body |
| **MCP** | `autonomous_pending_items` (read-only), with optional `state` and `automation_id` |
| **REST API** | `GET /api/autonomous/pending-items`, optionally `?state=waiting&automation_id=<id>`; an unknown state is refused with `400:` |
| **Comm channel** | `autonomous pending-items [waiting\|attached\|done] [automation-id]` |
| **Web UI** | Automata tab → Automation view → **Overview** sub-tab → the **Pending items** card, refreshed every 30 seconds: the policy and auto-resume in effect, the file registry line, every Automation that is held, and every item with its attach control |

## A file registry

You may already keep your list of work in a file: a table in a Markdown file.
You can point the daemon at it, and it copies the rows in as pending items, so
you do not type each one twice. This is optional, and it is one way: the daemon
**only reads** the file. It never writes to it, and an item you attach or finish
here is never written back.

Set the path, and tell the daemon how to read your table. Every setting has a
default, so you only change what your file does differently.

| Setting | What it tells the daemon | Default |
|---|---|---|
| `pending_item_source.path` | The file to read. Empty means no file registry | empty |
| `pending_item_source.id_pattern` | A regular expression. Only a row whose id cell matches it becomes an item | `^\S+$` (any non-blank id) |
| `pending_item_source.id_column` | Which column holds the id: a header name or a column number from 1 | `1` |
| `pending_item_source.title_column` | Which column holds the title | `2` |
| `pending_item_source.state_column` | Which column holds the state. Empty means the table has none | empty |
| `pending_item_source.done_values` | The state words that mean the work is done | `done`, `closed`, `shipped` |
| `pending_item_source.on_missing_row` | What to do with an item whose row has disappeared from the file: `keep` or `drop` | `keep` |

A column setting is a **header name** (matched without regard to upper or lower
case) or a **1-based column number**. A header name wins when a header carries
exactly that text.

### An example with a different id pattern and columns

Suppose your file lists work by short names instead of numbers, with the id in
the first column, the work in the second and a status in the third:

```
| Slug        | Work                        | Status  |
|-------------|-----------------------------|---------|
| guide       | Write the migration guide   | open    |
| move-logs   | Move logs to the new disk   | shipped |
| key-rotate  | Rotate the backup keys      | open    |
```

Read it with these settings (here the path is relative to the daemon's default
project directory; an absolute path is used as it is):

| Setting | Value |
|---|---|
| `pending_item_source.path` | `registry/work.md` |
| `pending_item_source.id_pattern` | `^[a-z]+(-[a-z]+)*$` |
| `pending_item_source.id_column` | `Slug` |
| `pending_item_source.title_column` | `Work` |
| `pending_item_source.state_column` | `Status` |
| `pending_item_source.done_values` | `done, closed, shipped` |

Then read the file:

```
$ datawatch autonomous pending-items-refresh
Refreshed 2031-03-02 10:14 UTC: 3 rows, 3 added, 0 updated, 1 done, 0 dropped, 0 kept, 0 skipped
```

The result is three items: *Write the migration guide* and *Rotate the backup
keys* are `waiting`, and *Move logs to the new disk* is `done`, because its
status `shipped` is one of the done values. Each item's `ref` is the text of its
id cell (`guide`, `move-logs`, `key-rotate`), and its source is `file`.

If the id column holds numbers like `12` or codes like `OPS-12`, only the
pattern changes: `^\d+$` or `^OPS-\d+$`. The daemon never assumes a numbering
sequence.

### How a row is read

- Every pipe table in the file is looked at; the first line of a table is its
  header, and a table is used only when its header resolves both the id column
  and the title column. Tables inside a fenced code block are ignored.
- A cell has its surrounding spaces, backticks and emphasis marks removed, and a
  link is reduced to its text.
- A row is **skipped** (and counted as skipped) when its id does not match the
  pattern or its title is empty. A row with a blank id is ignored without being
  counted. If the same id appears twice, the first row wins.
- The file must be a regular file of at most 2 MiB. A relative path may not leave
  the project directory, by `..` or by a symbolic link.

### When the file is read

The daemon reads the file registry **when it starts**, and **whenever you ask**
with the refresh action. It does not poll. Reading it again on an unchanged file
changes nothing.

| Method | How |
|---|---|
| **CLI** | `datawatch autonomous pending-items-refresh` |
| **MCP** | `autonomous_pending_items_refresh` |
| **REST API** | `POST /api/autonomous/pending-items/refresh` |
| **Comm channel** | `autonomous pending-items-refresh` |
| **Web UI** | The **Pending items** card → **Read the file registry now** (shown when a file registry is configured) |

### What a read changes

| Row | What happens |
|---|---|
| A new row | A new `waiting` item with source `file`, and its `ref` set to the id cell. A new row that is already done is added as `done` |
| A row whose title changed | The item's title is updated |
| A row whose state is one of the done values | The item becomes `done`. An Automation held on it is released and moves on. A `done` item stays `done` |
| An item whose row has disappeared | `on_missing_row` decides: `keep` leaves the item exactly as it is; `drop` removes it, but only if it is still `waiting` and is not a member of any Automation. Anything else stays and is counted as kept |

An item you added yourself (source `internal`) is never touched by a read. The
reply counts the rows added, updated, done, dropped, kept and skipped. If the
file cannot be read (it does not exist, it leaves the project directory, it is
not a regular file, it is too large, it has no table with the columns you named,
or the id pattern is not a valid expression), the reply carries the error, the
registry is left as it was.

## With no file registry

Leave `pending_item_source.path` empty, which is the default, and there is no
file registry. Everything above still works: you add items yourself, put them in
Automata, and attach Automata to them. The six other source settings do nothing,
the **Pending items** card says *No file registry is configured*, and the refresh
action reports that nothing is configured and changes nothing. Nothing is ever
read from a document unless you set a path.

## The policy and auto-resume

| Setting | Allowed | Default | What it changes |
|---|---|---|---|
| `pending_item_policy` | `hold`, `skip` | `hold` | Whether an Automation waits at a waiting item (`hold`) or goes past it (`skip`) |
| `pending_item_auto_resume` | `true`, `false` | `true` | Whether an attach resumes an Automation that was blocked on the item |

Both are read live: a change applies the next time an Automation reaches a
pending item or an Automaton is attached, with no restart. An unset policy, or a
word that is not one of the two, reads as `hold`, the safe choice. A write of any
other word is refused on every surface and nothing is saved.

## Changing the settings

| Method | How |
|--------|-----|
| **YAML** | The daemon's `config.yaml` → `autonomous:` → `automation:` → `pending_item_policy: hold`, `pending_item_auto_resume: true` and a `pending_item_source:` block with `path`, `id_pattern`, `id_column`, `title_column`, `state_column`, `done_values` (a list) and `on_missing_row` |
| **CLI** | `datawatch config set autonomous.automation.pending_item_policy skip` and, for the registry, `datawatch config set autonomous.automation.pending_item_source.path registry/work.md` |
| **Web UI** | Settings → General → Automata settings → **Pending items**: one field for each of the nine settings, each with a help link that opens its entry in the definitions |
| **REST API** | `PUT /api/config` with `{"autonomous.automation.pending_item_policy": "skip"}`, or `PUT /api/autonomous/config` with the `automation` object; `GET /api/config` shows the value in effect |
| **Comm channel** | `configure autonomous.automation.pending_item_policy=skip` |

The MCP tool `config_set` takes the same dotted key and value, and
`autonomous_config_set` takes the matching `automation_pending_item_*` argument
for each key. A list setting such as `done_values` is written as comma
separated words on the command line, in chat and in `config_set`, and as a list
in YAML and in a REST body. A value that is not allowed is refused with an error
that names the allowed words, and nothing is written.

| Key | Meaning | Default | Allowed |
|---|---|---|---|
| `autonomous.automation.pending_item_policy` | Hold at a waiting item, or skip it | `hold` | `hold`, `skip` |
| `autonomous.automation.pending_item_auto_resume` | Resume a blocked Automation when an Automaton is attached | `true` | `true`, `false` |
| `autonomous.automation.pending_item_source.path` | The file registry to read | empty | A file path; empty means none |
| `autonomous.automation.pending_item_source.id_pattern` | Which id cells count as items | `^\S+$` | A valid regular expression, at most 512 characters |
| `autonomous.automation.pending_item_source.id_column` | The id column | `1` | A header name or a number from 1 |
| `autonomous.automation.pending_item_source.title_column` | The title column | `2` | A header name or a number from 1 |
| `autonomous.automation.pending_item_source.state_column` | The state column | empty | A header name or a number from 1; empty means none |
| `autonomous.automation.pending_item_source.done_values` | State words that mean done | `done`, `closed`, `shipped` | A list of non-blank words, compared without regard to case |
| `autonomous.automation.pending_item_source.on_missing_row` | What to do when a row disappears | `keep` | `keep`, `drop` |

## Base requirements

- A running daemon with the Automata engine enabled.
- For a hold to mean anything, an Automation with the item as a member. An item
  on its own does nothing.
- For a file registry, a readable file with a pipe table, and a path set.

## Worked example

A team runs an Automation, *Release train*, with four members. The third is work
that nobody has written up yet: the migration guide. They want the train to stop
there and wait, not to run past it.

1. **Record the work.** `datawatch autonomous pending-item-add --title "Write
   the migration guide"` replies *Recorded pending item a1b2c3d4 (waiting)*.
2. **Put it in the chain.** `datawatch automation insert 5c20 --pending-item
   a1b2c3d4 --after m2 --reason "Waits on the design decision"`. The Automation
   is a draft, so the member lands after `m2` at once. They activate it.
3. **The train runs.** The first two members finish. The cursor reaches the third
   member, which is a waiting item. The Automation does not start anything: it
   becomes blocked, with the reason *member "Write the migration guide" is a
   pending item waiting for an Automaton to be attached*. The fourth member
   waits behind it. The **Pending items** card lists the hold.
4. **The design is settled.** The team writes the Automaton, decomposes it and
   approves it. It has the id `7e41`.
5. **Attach it.** `datawatch autonomous pending-item-attach a1b2c3d4 --automaton
   7e41`. The third member becomes an Automaton member for `7e41`, in the same
   place. The item is `attached`. Auto-resume is on, so the train resumes and
   starts `7e41`.
6. **It finishes.** When `7e41` completes, the item becomes `done` and the train
   goes on to the fourth member.

Had the policy been `skip`, the train would have passed the third member at step
3 without stopping, and the item would have stayed `waiting`.

## What it never does

It never starts work for a pending item: there is nothing to start until an
Automaton is attached. It never reads or writes a file you did not point it at,
and it never writes to the file registry. It never assumes a numbering sequence,
a file name or a repository layout. It never removes an item that is attached,
done or a member of an Automation because a file row disappeared. And it never
changes a `done` item back.
