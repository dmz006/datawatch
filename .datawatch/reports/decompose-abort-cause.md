# Decompose abort (SIGABRT, 19.5G peak) — cause report

Cause: The decompose-lint pass (`decomposeLintHook` → `LintTasksIn` rule `script_invokes_known_flag` → `probeCommandHelp` in `internal/autonomous/decompose_lint_script_help.go`) really executes the command prefix named in an existing verification script inside the daemon process: after `<prefix> --help` and `<prefix> -h` it runs the **bare prefix** as a third attempt (for `go ...` both help forms exit 2, so the bare `go test -race -run ... ./pkg` always runs), with no `cmd.Dir`, no process group, no `WaitDelay` and an unbounded `CombinedOutput` buffer, so one probe can run a whole race-detector build/test (or a streaming command) in the daemon's cgroup and heap for far longer than the nominal 5 s. This is the most probable cause of the 19.5G peak 1-2 s after "output file ready … treating as complete"; the exact step from that memory growth to SIGABRT is not proven here (see below), and the parse path and the `sh -c` probe are ruled out as the primary cause.

Evidence:
- coredumpctl: `command -v coredumpctl` returned nothing, so the tool is missing on this host. No `coredumpctl list` / `info` was possible, and no signal, faulting-thread frames or memory figures could be copied. The Go-level text of the abort is also unavailable to this task, because `daemon-crash.log` lives in the daemon data directory, outside the permitted scope.
- Why "SIGABRT with no panic text" is expected for any Go fatal or panic: `cmd/datawatch/main.go:458` calls `debug.SetTraceback("crash")` (any Go panic or `fatal error` then ends in SIGABRT and a core dump) and `main.go:478` calls `dupStderrTo(f)` (`cmd/datawatch/dup_unix.go:13`), which dup2s fd 2 into `<data>/daemon-crash.log`. The runtime's panic or fatal text therefore goes to that file, never to the journal. The first thing to read for the real Go-level message is `daemon-crash.log` right after the "=== datawatch v… started pid=… ===" line of the crashing pid. The one open question is whether it holds `fatal error: runtime: out of memory` (daemon heap), a panic in the lint/parse path, or nothing (a child or the cgroup killed the process).
- Poll loop `cmd/datawatch/session_judgment.go:686-689`: `relocate()` returns the file content and the function returns it. That is a bounded read and cannot abort. The caller then reaches `ParsePlanning` and `decomposeLintHook` (`internal/autonomous/manager.go:3847/3867` and `4055/4068`; `planning_reattach.go:40/45`) with no `recover` anywhere on that path.
- Parse path ruled out: `ParsePlanning` / `cleanLLMJSON` / `stripLineComment` (`internal/autonomous/decompose.go:365,463,484`) are linear in the input. `normalizeRulesApplied` (`decompose.go:332-357`) cannot loop forever (the `utf8.ValidString` trim loop ends at the empty string) and caps entries and bytes. There is no recursion and no cgo, so a ~5 KB plan cannot allocate GB there. `cleanLLMJSON` recompiles two regexes per call, which is minor.
- Lint non-exec parts ruled out: `RunVerifyScriptPreflight` (`verify_script_preflight_run.go`) only reads files (`readProjectFile`, 1 MiB buffer per read) and runs `sh -n <tmp script>` (`verify_script_preflight.go:47`), which is syntax-only and exits quickly. `verifyScriptContent` follows `source` helpers one level, deduplicated, with no recursion. `ensurePlanIDs` and `ApplyTaskTemplates` are bounded.
- `defaultScriptHelpProbe` (`decompose_lint_script_assertions.go:51-64`) is ruled out as the primary cause: it runs `sh -c "command -v <cmd>"` and `sh -c "<cmd> --help"` only for names matching `^[a-z][a-z0-9_.-]{0,63}$` that are not shell builtins, capped at `scriptHelpMaxProbes=16` per script and never run bare. It does share the weaknesses of lines below (output buffered without a cap, direct child only killed on timeout), so it needs the same hardening.
- `probeCommandHelp` confirmed (`decompose_lint_script_help.go:170-204`): `attempts := [][]string{{"--help"}, {"-h"}, {}}` (line 183), success requires `err == nil` (line 194), `exec.CommandContext(ctx, bin, args...).CombinedOutput()` (line 189) with no `cmd.Dir`, no `Setpgid`, no `WaitDelay`. `exec.LookPath(prefix[0])` also resolves the daemon's own `datawatch` binary, so a script line such as `datawatch restart --x` would run bare `datawatch restart` inside the daemon (not demonstrated; argued from code). The rule is in the default pack with block severity (`decompose_lint_rules.go:146`) and the default lint mode is shadow, so it runs on every decompose whose verification script already exists in the project directory.
- Real exit codes on this host: `go test --help` rc=2, `go test -h` rc=2, `go build --help` rc=2 (so `go` always falls through to the bare prefix); `git diff --help` rc=0, `make --help` rc=0.
- Reproduction with fakes (throwaway test `internal/autonomous/zz_abort_repro_test.go`, run with `env -u TMUX -u TMUX_TMPDIR go test ./internal/autonomous -run TestZZAbortRepro -v`, file deleted afterwards; `scriptHelpProbe` replaced by a fake, fake `go` and `git` scripts first on PATH). Synthetic plan: one story, 5 merge-shadow race tasks, each with a `.datawatch/verify/merge-shadow-race-N.sh` that existed in the project dir; the plan was 2600 bytes, not 4858, but parse cost is linear so the size is not material:
  - `Manager.Decompose` finished `needs_review` in 43 ms with no panic, so the parse and lint logic is not itself a crash source with fake binaries.
  - The fake `go` log shows the real lint pass executing the full prefix three times: `go test -race -run TestMergeShadowCompare ./internal/autonomous --help`, `... -h`, then **`go test -race -run TestMergeShadowCompare ./internal/autonomous`** (bare, a real test run). The same happened for `git diff`, `git diff --name-only main...HEAD`: 9 real executions for 5 tasks, plus 10 fake `command -v` probes.
  - Output buffering: a fake `streamer` command emitting 256 MiB made `probeCommandHelp` hold 256 MiB and allocate 1536 MiB total (about 6x amplification from buffer growth). At memory speed a 5 s probe can emit well over 15 GiB, and the whole buffer is the daemon's own heap, which is consistent with a 19.5G peak and a Go out-of-memory fatal that GOTRACEBACK=crash turns into SIGABRT.
  - Timeout is not a bound: a fake `holder` command (`(sleep 8) & exec sleep 60`) with `scriptHelpProbeTimeout` set to 1 s took 24.0 s for the 3 attempts (8 s each, the grandchild's lifetime). The context kills only the direct child and `Wait` blocks until every holder of the pipe exits, so a real `go test -race` (compiler and test-binary grandchildren) blocks the decompose goroutine until it finishes, with all of its memory counted in the daemon's cgroup.
- Not proven: the daemon dying with SIGABRT specifically (as opposed to the cgroup OOM killer's SIGKILL or a child's failure) needs `daemon-crash.log` or coredumpctl output from the incident, neither readable here. Any panic in the unguarded lint/parse path would also produce exactly this signature, but none was reproducible with the fakes.

Fix: Make the lint pass unable to run anything unbounded and unable to take the daemon down. Change `internal/autonomous/decompose_lint_script_help.go`: in `probeCommandHelp` drop the bare-prefix attempt (and the `-h` attempt) so only `<binary> --help` is ever run, never probe a prefix longer than the binary plus at most one subcommand word, never probe `datawatch` or the daemon's own executable (`os.Executable()`), set `cmd.Dir` to a scratch dir, `SysProcAttr{Setpgid:true}` and kill the whole group on timeout (reuse the pattern in `internal/autonomous/script_gate.go` / `script_gate_unix.go`), set `cmd.WaitDelay` (about 2 s), and replace `CombinedOutput` with a size-capped writer (about 64 KiB). Apply the same process-group, `WaitDelay` and output-cap hardening to `defaultScriptHelpProbe` in `internal/autonomous/decompose_lint_script_assertions.go`. In `internal/autonomous/decompose_lint_hook.go` wrap the `findings` closure and `applyTemplates` in `decomposeLintHook` (and the preflight-only branch) with a `recover` that records a named lint-skipped finding and keeps the plan. In `internal/autonomous/manager.go` (both ParsePlanning/`decomposeLintHook` sites, ~3847 and ~4055) and `internal/autonomous/planning_reattach.go` wrap parse + lint in a `recover` that converts a panic into a named `ErrPlanningParse`-style error (new typed error in `internal/autonomous/decompose.go` alongside `ParsePlanning`, with the raw-output length and a truncated head) so a bad or hostile plan fails the one PRD instead of aborting the daemon. Add tests for each: bare prefix is never executed, output cap, timeout with a background grandchild returns within the bound, and a panicking lint step is recovered. Also read `<data>/daemon-crash.log` after the crashing pid's start marker to confirm the Go-level message.
